# Вехи: как пользоваться

Практическое руководство для работы с вехами (milestones) в ANotes — для тех,
кто работает в интерфейсе, а не в коде.

---

## 1. Что такое веха и чем она отличается от эпика

**Веха — это точка на оси времени.** Ключевое событие или дата, по которой удобно
измерять готовность: релиз 1.0, демо заказчику, конец бета-теста, дедлайн по договору.

**Эпик — это отрезок.** Направление работы, которое тянется во времени: «Уведомления»,
«Переезд на новую БД», «Редизайн личного кабинета».

Это **две независимые оси**, и одна не заменяет другую:

| | Эпик | Веха |
|---|---|---|
| Отвечает на вопрос | «что делаем» | «к какому числу» |
| На шкале | полоса | точка (ромб) |
| Состав | задачи одного направления | задачи из **разных** эпиков |
| Задача принадлежит | одному эпику | одной вехе |
| Исполнитель | нет | нет |
| Свой статус | нет (считается по задачам) | нет (считается по задачам) |

**Пример.** Задача «Web Push: серверные подписки» входит:
- в **эпик** «Уведомления» (это про содержание — над чем работаем);
- в **веху** «Релиз 1.2» (это про срок — к 20 сентября должно быть в проде).

Обе привязки живут одновременно и не мешают друг другу.

**У эпика вехи быть не может.** Это осознанное отличие: в Jira эпик — обычная задача
с полем Fix Version, в GitLab (с версии 18.2) майлстоун тоже можно назначить эпику.
У нас — нет, и вот почему. Веха собирает конкретные задачи с общим сроком, а эпик
тянется через несколько релизов сразу — один срок на него повесить нельзя, не соврав
про остальные. Нужен «эпик к дате» — это и есть веха: заведите веху и положите в неё
те задачи эпика, что должны попасть в релиз.

### 1.1. Если вы приходите из другой системы

Короткий ответ для тех, кто мигрирует: веха — это Fix Version / релизная версия,
**не** спринт. Спринтов как отдельной сущности здесь нет.

| Ваш опыт | Здесь |
|---|---|
| Jira: Fix Version, Release | **Веха** |
| GitHub / GitLab: Milestone | **Веха** |
| Jira: Epic | **Эпик** (но без вехи и без исполнителя) |
| Jira: Sprint, GitLab: Iteration | отдельной сущности нет; ближайшая аналогия — веха с датой конца итерации |
| MS Project: веха как событие нулевой длительности | у нас веха — это срок, к которому привязана группа задач |

В Jira и GitLab время разнесено на две оси — спринт/итерация (ритм команды) и
версия/майлстоун (релиз). Здесь ось одна: веха. Меряете релизами — заводите
вехи-релизы; работаете итерациями — вехи с датой конца спринта; можно и то и другое
в одном проекте, список вех сортируется по дате.

Три отличия, о которых стоит знать сразу:

- у задачи ровно **одна** веха (в Jira их может быть несколько). Если правка идёт
  в два релиза (бэкпорт в ветку поддержки + текущая версия), заведите на бэкпорт
  отдельную задачу под свою веху — это всё равно отдельный PR в другую ветку;
- эпик к вехе **не привязывается**;
- отдельного поля «резолюция» нет — выполненность определяется **закрывающим
  статусом проекта**.

## 2. Где находятся вехи

Отдельного пункта в верхнем меню нет — вехи всегда про один проект.

**Открыть:** страница **«Проекты»** → в строке нужного проекта нажать иконку‑ромб
(◆), она рядом с иконками «Дорожная карта» и «База знаний».

Адрес страницы: `…/projects/<id проекта>/milestones`.

---

## 3. Создание вехи

На странице вех — кнопка **«+ Веха»** (справа вверху).

| Поле | Обязательно | Примечания |
|---|---|---|
| **Название** | да | Уникально в пределах проекта. Два «Релиз 1.0» в одном проекте создать нельзя — будет ошибка. |
| **Срок** | да | Веха без даты — это просто ярлык. Если точная дата неизвестна, поставьте примерную и потом поправьте. |
| **Описание** | нет | Поддерживается Markdown. Например: что входит в релиз, ссылка на changelog. |

**Пример заполнения:**

```
Название:   Релиз 1.2
Срок:       20.09.2026
Описание:   Web Push, экспорт отчётов в CSV, тёмная тема.
            Чек-лист приёмки: docs/release-1.2.md
```

Только что созданная веха — пустая (0 задач). Это нормально, задачи добавляются
отдельно (см. §5).

## 4. Что показывает список вех

Вехи идут **по возрастанию срока** — ближайший дедлайн сверху.

```
◆ Релиз 1.2                    Готова к закрытию      осталось 12 дней
   ████████████████████  12/12 · 100%                      20.09.2026

◆ Демо заказчику                                      осталось 34 дня
   ████░░░░░░░░░░░░░░░░  2/9 · 22% · 1 просрочена           12.10.2026

◇ Релиз 2.0                                           осталось 89 дней
   ░░░░░░░░░░░░░░░░░░░░  0/15 · 0%                           06.12.2026
```

- **Ромб** слева окрашен по состоянию вехи (см. §6). Закрытая веха — залитый серый ◆,
  открытая — контурный ◇/◆.
- **Полоса прогресса** — доля закрытых задач (`закрыто / всего`). Показывается, когда
  задач больше одной.
- **`12/12 · 100%`** — закрыто из всего, и процент.
- **`1 просрочена`** — сколько незакрытых задач вехи уже перешли свой срок (см. §7).
- **Дата справа** — срок вехи; **«осталось N дней»** / **«просрочена на N дней»** —
  сколько до него.

**Переключатель «Показать закрытые (N)»** вверху — по умолчанию завершённые вехи
скрыты, чтобы список был про то, что впереди. Появляется, только когда закрытые
вехи есть.

Клик по строке открывает страницу вехи.

## 5. Как добавить задачи в веху

Три способа — выбирайте удобный:

### Способ 1. Со страницы вехи — «Добавить»

Открыть веху → блок **«Задачи вехи»** → кнопка **«+ Добавить»**. Откроется список
**задач проекта, у которых пока нет вехи**. Отметьте нужные, нажмите
«Добавить (N)».

Подходит, когда веха уже намечена и надо быстро набрать в неё работу из бэклога.

### Способ 2. На странице самой задачи

Открыть задачу → правая панель → селектор **«Веха»** → выбрать веху из списка
(там только открытые вехи проекта). Сохраняется сразу, кнопки «Сохранить» нет.

Чтобы **убрать** задачу из вехи — тот же селектор, пункт **«Без вехи»**.

Подходит, когда планируете конкретную задачу: «этот баг чиним к демо».

### Способ 3. При создании задачи

В форме «Новая задача» есть поле **«Веха»** (появляется, когда у выбранного проекта
есть открытые вехи). Задача сразу создаётся привязанной.

## 6. Состояния вехи

Состояние **считается автоматически** из состава задач и срока — вручную его не
выставить. Хранится только факт «открыта / закрыта».

| Состояние | Что значит | Когда возникает |
|---|---|---|
| **Запланирована** (`PLANNED`) | Работа не начата | Ни одна задача вехи ещё не закрыта |
| **В работе** (`IN_PROGRESS`) | Идём по плану | Часть задач закрыта, темп нормальный |
| **Под риском** (`AT_RISK`) | Не успеваем по темпу | Дней до срока меньше, чем осталось незакрытых задач |
| **Просрочена** (`LATE`) | Срок вехи прошёл, работа осталась | Дата вехи в прошлом, не все задачи закрыты |
| **Готова к закрытию** (`READY`) | Всё сделано, но веха ещё открыта | Все задачи закрыты, а веху человек ещё не закрыл |
| **Закрыта** (`CLOSED`) | Завершена | Веху закрыл человек (§8) |

**Важно:** «1 задача просрочена» в списке — это **отдельный индикатор**, он не то же
самое, что состояние `LATE`. Веха может быть «В работе» (свой срок ещё впереди) и при
этом содержать просроченные задачи.

**«Под риском» — грубый сигнал, не прогноз.** Формула сравнивает число незакрытых
задач с числом дней до срока; трудоёмкость не учитывается — тридцать получасовых
задач за двадцать дней тоже дадут «Под риском». Оценка в часах не учитывается;
прогресс вехи считается по количеству задач. Burndown по стори-поинтам, как в Jira,
здесь нет — воспринимайте «Под риском» как повод пересмотреть план.

**Пример перехода состояний для «Релиз 1.2» (срок 20.09):**

- 1 сентября, 0/12 закрыто → **Запланирована**
- 10 сентября, 5/12 закрыто, 10 дней в запасе → **В работе**
- 17 сентября, 6/12 закрыто, осталось 3 дня, а задач 6 → **Под риском**
- 21 сентября, 11/12 закрыто → **Просрочена**
- 22 сентября, 12/12 закрыто, веху не трогали → **Готова к закрытию**
- 22 сентября, нажали «Закрыть веху» → **Закрыта**

## 7. «N задач просрочено» — что это и как убрать

На странице вехи и в списке может быть надпись вида **«· 1 просрочена»**.

**Что считается:** задача, привязанная к вехе, у которой одновременно:
- статус **не** закрывающий (задача в работе), и
- **её собственный** срок (поле «Срок» у задачи) — в прошлом.

Это **не** про срок вехи. У вехи «Демо заказчику» дедлайн 12 октября, а задача
«Подготовить стенд» со своим сроком 30 сентября уже висит — вот она и «просрочена».

**Иконка ⚠ в списке задач вехи — это другое:** она помечает задачи, чей срок
**позже** срока вехи (такая задача к дате вехи не успеет по определению).

**Как сделать, чтобы задача перестала быть просроченной** — любое из:

1. **Закрыть задачу.** На странице вехи в списке «Задачи вехи» поставьте галочку
   слева от задачи — она переедет в закрывающий статус проекта. Счётчик пересчитается
   сразу.
2. **Подвинуть срок задачи.** Открыть задачу → правая панель → «Срок» → поставить
   сегодняшнюю дату или позже. Либо очистить срок совсем — задача без срока в
   «просроченные» не попадает.

**Пример.** В вехе «Демо заказчику» — «1 просрочена». Открываем список задач вехи,
находим задачу с прошедшей датой и незакрытым статусом. Решаем:
- если работа реально сделана — ставим галочку, задача закрывается, «0 просрочено»;
- если работа ещё идёт, а старый срок нереалистичен — открываем задачу и ставим
  новый срок, скажем, 8 октября (до даты вехи). Тоже «0 просрочено», но задача
  осталась открытой.

## 8. Закрытие вехи

Кнопка **«Закрыть веху»** на странице вехи.

**Когда можно закрыть:** **в любой момент.** Ограничений нет.

- Незакрытые и даже просроченные задачи закрытию **не мешают** — релиз выпускают и
  с недоделанными пунктами.
- Если незакрытые задачи есть, интерфейс спросит подтверждение:
  «В вехе осталось N незакрытых задач… Закрыть сейчас?» — это предупреждение, а не
  запрет.
- Единственный отказ — попытка закрыть уже закрытую веху.

**Что происходит с задачами при закрытии:**

- Задачи **не удаляются** и **никуда не переносятся** — остаются привязанными к
  закрытой вехе.
- Если хотите перенести недоделанные задачи в следующую веху — это **отдельное
  действие**: на каждой задаче через селектор «Веха» выбрать новую веху (см. §5,
  способ 2).
- Факт закрытия с незавершёнными задачами фиксируется в журнале активности проекта
  отдельной записью.

**Закрытую веху нельзя пополнять.** Привязать к ней новую задачу не даст ни
интерфейс (в селекторе «Веха» на задаче закрытых вех нет), ни прямой запрос через
API или ИИ-агента — сервер вернёт «Нельзя добавлять задачи в закрытую веху»
(HTTP 400). То же — при попытке создать задачу сразу с закрытой вехой. Уже
привязанные задачи после закрытия остаются на месте. Нужно доложить работу в веху —
сначала откройте её заново (§9).

**Состояние «Готова к закрытию».** Когда все задачи вехи закрыты, а веху ещё не
трогали, на странице появляется баннер:

> **Все задачи вехи выполнены.** Веха собрана — закрыть её?

Это подсказка. Система **сама веху не закрывает** — решение всегда за человеком
(релиз может быть собран, но ещё не выпущен).

**Пример.** «Релиз 1.2»: 12/12 задач закрыто, состояние «Готова к закрытию», висит
баннер. QA прогнали регресс, релиз выкатили в прод — нажимаем «Закрыть веху». Веха
уходит в «Закрыта», в списке скрывается (пока не включить «Показать закрытые»).

**Чего система не фиксирует.** После закрытия веха не помечается как «закрыта с
опозданием» — сравнить фактический срок с плановым в интерфейсе нельзя. Веха,
которая съехала на неделю, и веха, закрытая день в день, в списке закрытых
выглядят одинаково; сам факт закрытия остаётся только в журнале активности проекта.

---

## 9. Открыть веху заново

Если веху закрыли рано или ошиблись — на странице закрытой вехи кнопка
**«Открыть заново»**. Веха снова становится активной, состояние пересчитывается по
текущему составу задач.

Повторно открыть уже открытую нельзя (кнопки просто не будет).

---

## 10. Удаление вехи

Меню **«⋯»** на странице вехи → **«Удалить веху»**.

- **Если задач в вехе нет** — простое подтверждение, веха удаляется.
- **Если задачи есть** — откроется окно с выбором. **Задачи не удаляются ни при
  каком варианте** (веха — это ярлык срока, а не контейнер работы):

  | Вариант | Что происходит |
  |---|---|
  | **Открепить задачи и удалить** | Задачи остаются в проекте, но без вехи |
  | **Перенести задачи и удалить** | Сначала выберите другую открытую веху в списке — задачи переедут туда, потом веха удалится |

**Пример.** Веху «Хотфикс 1.1.3» завели зря, в ней 3 задачи. Открываем удаление,
в селекторе выбираем «Релиз 1.2», жмём «Перенести задачи и удалить» — три задачи
теперь в «Релиз 1.2», лишняя веха исчезла.

---

## 11. Вехи на дорожной карте

Открыть **«Дорожная карта»** проекта (иконка‑календарь в строке `/projects`).

Вехи рисуются **вертикальными линиями с ромбом** поверх полос эпиков, по своим
срокам. Над шкалой — строка «Вехи» с подписями (на широком экране). Клик по ромбу
ведёт на страницу вехи.

Смысл: сразу видно, **попадает ли работа эпика в релиз**. Если полоса эпика
«Уведомления» заканчивается 25 сентября, а линия вехи «Релиз 1.2» стоит на
20 сентября — эпик в этот релиз не укладывается, часть работы уедет дальше.

---

## 12. Вехи в списке задач

На странице **«Задачи»**:

### Фильтр «Веха»

Выпадающий список (работает, когда выбран проект):

- **«Любая веха»** — фильтр выключен;
- **«Без вехи»** — только задачи, не привязанные ни к одной вехе (удобно вычищать
  бэклог: «что у нас вообще не распределено по релизам»);
- **конкретная веха** — только её задачи.

### Режим «По вехам»

Переключатель вида (рядом с «Список», «По эпикам», «Доска») → **«По вехам»**.

Задачи проекта группируются по вехам, по возрастанию срока; в конце — группа
**«Без вехи»**. У каждого заголовка: прогресс, счётчик, срок, число просроченных.
По умолчанию группы свёрнуты — сначала видно картину по релизам, разворачиваете
нужную.

- `Shift + ←` / `Shift + →` — свернуть / развернуть все группы.
- В строке задачи виден её **эпик** — веха собирает работу из разных направлений,
  и полезно видеть, откуда задача.

## 13. Типовые сценарии

### Спланировать релиз

1. Проект → ◆ → «+ Веха»: «Релиз 1.3», срок 15.11.2026.
2. Открыть веху → «+ Добавить» → отметить задачи из бэклога, которые входят в релиз.
3. Что-то ещё не заведено — создать задачу с полем «Веха: Релиз 1.3».
4. Дальше следить за состоянием: «Под риском» / число просроченных — сигнал, что
   план поехал.

### Подготовка к демо заказчику

1. «+ Веха»: «Демо 14.10», срок 14.10.2026, в описании — сценарий демо.
2. На каждой задаче, которую надо показать, выставить «Веха: Демо 14.10».
3. На дорожной карте проверить, что полосы нужных эпиков заканчиваются левее ромба
   вехи.
4. Задачи с ⚠ (срок позже даты вехи) — либо подвинуть им срок, либо честно вынести
   из демо (снять веху).

### Релиз выехал — перенести хвост

1. Веха «Релиз 1.2», состояние «Просрочена», 10/12.
2. Две незакрытые задачи открываем и ставим им «Веха: Релиз 1.3».
3. Возвращаемся в «Релиз 1.2» — теперь 10/10, «Готова к закрытию».
4. «Закрыть веху». Хвост уехал в следующий релиз, история чистая.

### Разобрать нераспределённый бэклог

1. «Задачи» → выбрать проект → фильтр «Веха: Без вехи».
2. Пройтись по списку, каждой задаче проставить подходящую веху (или оставить без —
   если это фон, не привязанный к дате).

## 14. Коротко

- Веха = **дата**, эпик = **направление**; у задачи может быть и то, и другое.
- **Срок обязателен**, название уникально в проекте.
- Состояние и прогресс считает система — вручную не трогаются.
- **«Просрочена»** = незакрытая задача со своим сроком в прошлом → закрыть задачу
  или подвинуть ей срок.
- Закрыть веху можно **когда угодно**, даже с незакрытыми задачами; задачи при этом
  не пропадают и сами никуда не переезжают.
- Удаление вехи **никогда не удаляет задачи** — только открепляет или переносит.
