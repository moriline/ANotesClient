Прочитал. Всплывающее окно здесь — симптом, а причина в другом: **на одном экране живут две несовместимые модели сохранения**.

Статус и исполнитель ждут кнопки «Сохранить». Эпик, стоящий в той же правой панели, сохраняется сразу. Человек не может вывести из внешнего вида, какое поле как себя ведёт — и именно из этого расхождения растут и липкая плашка, и охранник ухода, и `beforeunload`.

## Правильная граница проходит не там

Не «поля задачи против остального», а **дискретный выбор против длинного текста**.

| | Сохранять | Почему |
|---|---|---|
| Статус, исполнитель, приоритет, срок, дата начала, оценка, теги, эпик | **сразу** | один клик, намерение однозначно, терять нечего |
| Название, описание | **явно** | набор текста непрерывен и прерываем |

Выбор в `USelectMenu` — это уже принятое решение. Заставлять человека подтверждать его второй раз кнопкой внизу экрана — просить дважды сказать одно и то же. А набор абзаца — процесс, который нельзя фиксировать посреди слова.

Так устроены и Linear, и GitHub, и Jira. Совпадение не случайное.

## Что происходит с каждым всплывающим окном

| Окно | Судьба |
|---|---|
| Плашка «Есть несохранённые изменения» | сжимается до кнопок **внутри** блока описания |
| Confirm «Уйти без сохранения?» | **исчезает** — заменяется черновиком |
| `beforeunload` | **исчезает** — заменяется черновиком |
| Диалог 409 «Перезагрузить / Перезаписать» | **исчезает** — заменяется разрешением по полю |

## Черновик вместо охранника ухода

Confirm при уходе просит человека принять решение под давлением, и оба варианта плохие: «остаться» мешает, «уйти» уничтожает текст.

Черновик не спрашивает ничего:

```ts
// composables/useDraft.ts
export function useDraft(taskId: Ref<number>, field: string) {
  const key = computed(() => `draft:task:${taskId.value}:${field}`)
  const draft = ref<string | null>(null)

  onMounted(() => { draft.value = sessionStorage.getItem(key.value) })

  const save = useDebounceFn((v: string) => {
    try { sessionStorage.setItem(key.value, v) } catch {}
  }, 1000)

  const clear = () => sessionStorage.removeItem(key.value)
  return { draft, save, clear }
}
```

Вернулся на задачу — над редактором строка: «Есть несохранённый черновик от 14:32. [Восстановить] [Отбросить]». Закрыл вкладку случайно, открыл заново — текст на месте. Ни одного диалога.

`sessionStorage`, а не `localStorage`: черновик недельной давности вреднее, чем его отсутствие.

## Главное: конфликт по полю, а не по объекту

Сейчас `X-Expected-Version` сравнивает версию **всей задачи**. Из-за этого Анна поменяла исполнителя, вы поменяли срок — и вы получаете 409, хотя никакого конфликта нет: вы правили разные поля.

Так возникает большинство ваших окон 409. Они ложные.

```java
@PATCH
@Path("/{taskId}")
public Response patch(@PathParam("taskId") Integer taskId,
                      @HeaderParam("X-Expected-Version") Integer expected,
                      TaskUpdateRequest req) {

    var current = tasks.require(taskId);
    if (expected == null || current.version == expected) {
        return Response.ok(tasks.apply(taskId, req)).build();
    }

    // версия разошлась — смотрим, задели ли те же поля
    var changedSince = revisions.fieldsChangedSince(taskId, expected);
    var iAmChanging  = req.presentFields();
    var overlap      = Sets.intersection(changedSince.keySet(), iAmChanging);

    if (overlap.isEmpty()) {
        return Response.ok(tasks.apply(taskId, req)).build();   // конфликта нет
    }

    return Response.status(409).entity(new FieldConflictResponse(
        overlap.stream().map(f -> new FieldConflict(
            f,
            changedSince.get(f).value(),      // чужое значение
            changedSince.get(f).authorName(), // кто поставил
            changedSince.get(f).changedAt(),  // когда
            req.valueOf(f)                    // ваше значение
        )).toList(),
        current.version)).build();
}
```

Для этого нужен журнал изменений полей — у вас `activity` с полем `details` уже есть, туда достаточно писать `{ field, from, to }` при каждом `PATCH`.

## Разрешение — в поле, не в модалке

Когда конфликт настоящий, показывать его надо там, где он произошёл:

```
Статус
┌────────────────────────────────────────┐
│ Готово                              ▾  │
└────────────────────────────────────────┘
⚠ Анна поставила «На ревью» 2 минуты назад
  [ Оставить её ]  [ Поставить моё ]
```

Три отличия от модалки, и все существенные:

- **Видно, что именно теряется.** «Перезаписать» в вашем текущем диалоге уничтожает чужую правку вслепую — человек не знает, что там было.
- **Остальные поля не откатываются.** Сейчас «Перезагрузить» сбрасывает все локальные правки ради одного конфликта.
- **Не блокирует экран.** Можно дописать комментарий, посмотреть историю, потом решить.

## Свежесть вместо неожиданности

Раз задача открыта минутами, показывайте изменения по мере их появления. Опрос раз в 30 секунд (или SSE, если уже заведёте его для уведомлений):

- поле изменилось, человек его **не трогал** → обновить тихо, с подсветкой на две секунды;
- поле изменилось, человек его **правит** → пометка «Анна изменила это поле» под полем, без перезаписи.

Тогда 409 почти перестают возникать: окно между чтением и записью сжимается с минут до секунд.

## Две мелочи из вашего описания

**`changeParent` и `convertType` не шлют версию.** Это структурные изменения — перенос задачи в другой эпик и смена вида. Они важнее срока, а защищены слабее. Версию туда стоит добавить в первую очередь, а не в последнюю.

**«Перезаписать» повторяет PATCH без заголовка.** Это осознанный last-write-wins по кнопке, и он опасен именно тем, что человек не видит уничтожаемого. Если решите оставить кнопку — покажите рядом, что будет перезаписано.

## Порядок внедрения

1. **Пикеры сохраняются сразу.** Плашка остаётся только для названия и описания. Уже здесь исчезает большая часть трения.
2. **Черновик в `sessionStorage`.** Убирает `onBeforeRouteLeave` и `beforeunload`.
3. **Конфликт по полю на сервере.** Убирает ложные 409.
4. **Инлайн-разрешение.** Убирает диалог 409 окончательно.
5. **Опрос свежести.** Убирает и оставшиеся настоящие конфликты.

Первые два пункта — вечер работы каждый и не требуют трогать бэкенд.
