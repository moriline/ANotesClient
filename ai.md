# ANotes — интеграция ИИ через API

Документ описывает, как дать ИИ-агенту работать с менеджером задач через API, без встраивания моделей в бэкенд.

**Принятое решение: вариант 1 — прямой доступ по OpenAPI с обычным JWT.** Выбран как самый простой путь: не требует новых протоколов, расширений и таблиц. Использует уже существующую аутентификацию и проверенную тестами спецификацию. Вариант 2 (MCP) описан ниже как возможный следующий шаг.

---

## Общий принцип

ИИ становится **клиентом вашего API, а не функцией внутри бэкенда**.

Из проекта уходят LangChain4j, Ollama, промпты в Java, таймауты и circuit breaker вокруг модели — и заодно вся история с `NoOpEmbeddingModel`, приоритизированной через `@Alternative + @Priority`. Выбор модели становится делом пользователя: Claude, GPT, локальная — любая, лишь бы умела вызывать HTTP.

Это не усложнение, а вычитание кода.

# Вариант 1 — прямой доступ по OpenAPI ✅ ВЫБРАН

## 1.1 Почему он подходит

У вас **уже есть всё нужное**:

- OpenAPI-спека, актуальность которой проверяется тестом `OpenApiSpecTest` — она не разъедется с реальным API;
- явный список `PUBLIC_OPERATIONS`, ужатый до `register` и `login`, остальное под `bearerAuth`;
- работающая аутентификация на JWT;
- система прав `PermissionService` с проектными ролями, разрешаемыми из базы при каждом запросе.

Современные модели умеют вызывать REST по OpenAPI напрямую. Объём работы — один вечер, и почти весь он уходит не на код.

## 1.2 Чего не хватает: описания операций

Главная проблема на сегодня. В спецификации у операций **пустые `summary` и `description`**:

```
GET /api/tasks/{taskId}/summary :: None ::
PUT /api/tasks/{taskId}/summary :: None ::
GET /config/ai                  :: None ::
```

Модель, читающая такую спеку, видит путь и схему — и больше ничего. Она не понимает, что делает ручка, когда её вызывать и чем `PUT /summary` отличается от `PATCH /tasks/{id}`. Это гарантированно приведёт к неправильным вызовам.

Поэтому первый шаг — заполнить аннотации:

```java
@GET
@Path("/{taskId}")
@Operation(
    summary = "Получить задачу по номеру",
    description = """
        Возвращает задачу целиком: заголовок, описание, статус, исполнителя,
        теги, сроки, оценку и суммарное списанное время.
        Комментарии не входят — их отдаёт GET /api/tasks/{taskId}/comments.
        """)
public TaskResponse getTask(@PathParam("taskId") Integer taskId) { ... }
```

```java
@PUT
@Path("/{taskId}/summary")
@Operation(
    summary = "Записать краткое резюме задачи",
    description = """
        Перезаписывает поле summary. Резюме — 2-4 предложения для человека,
        который видит задачу впервые: суть работы, принятые решения,
        изменённые сроки, выявленные ограничения.
        Не меняет version задачи.
        """)
public TaskSummaryResponse setSummary(
    @PathParam("taskId") Integer taskId,
    TaskSummaryRequest request) { ... }
```

Правило простое: **описание операции — это и есть промпт**. Всё, что вы написали бы в системном сообщении модели, пишите в `description`. Модель прочитает его сама.

То же для параметров:

```java
@Parameter(description = "Название статуса из набора проекта. "
                       + "Получить список: GET /api/project-statuses/project/{projectId}")
@QueryParam("status") String status
```

## 1.3 Аутентификация: существующий JWT, без новых таблиц

### Что есть сейчас

`POST /api/auth/login` возвращает `AuthResponse`:

```json
{ "token": "eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9...",
  "username": "admin", "roles": ["USER"] }
```

Устройство токена:

| Поле | Значение |
|---|---|
| Подпись | RS256, приватным ключом `privateKey.pem` (`smallrye.jwt.sign.key.location`) |
| Проверка | `publicKey.pem` (`mp.jwt.verify.*`) |
| `iss` | `taskmind` |
| `aud` | `taskmind-api` |
| `sub` | целочисленный `userId` |
| `groups` | `["USER"]` либо `["USER","ADMIN"]` при `users.isAdmin` |
| `username` | дополнительный claim |
| `jti` | UUID, уникальный идентификатор токена |
| `exp` | +7200 c = 2 часа, из `smallrye.jwt.new-token.lifespan` |

Рефреша нет: по истечении срока нужен повторный `/api/auth/login`.

**Важно:** проектные роли (Admin, Manager, Developer, Guest, Client) в токен не попадают. Они живут в `projectMembers` + `projectRoles` и проверяются `PermissionService` при каждом запросе. Значит эти права не устаревают вместе с токеном — снятие роли действует мгновенно.

### Чей токен получает агент

Разберём варианты, прежде чем выбрать.

| Вариант | Кто в журнале активности | Права агента | Проблема |
|---|---|---|---|
| Обычный токен человека | человек | все его, включая ADMIN и удаление | агента не отличить от человека; агент может всё |
| Общая учётка `taskmind-agent` | «Агент» | одна роль на всех | непонятно, кто дал команду; общий доступ ко всем проектам; отзыв ломает всем |
| Отдельная учётка на каждого | «Агент Анны» | зеркало прав человека | лишние учётные записи, участие в проектах надо синхронизировать вручную |
| **Агентский токен самого человека** ✅ | «Дмитрий (через агента)» | права человека минус разрушительное | нужен второй тип токена |

**Выбран четвёртый вариант.** Не новая учётная запись, а второй тип токена для существующей.

Почему не общая учётка: если Анна, Дмитрий и вы подключите своих агентов к одному аккаунту, журнал скажет «Агент сменил статус TSK-104» — и кто попросил, останется неизвестным. Плюс общий аккаунт видит объединение всех проектов, а отобрать доступ у одного человека нельзя, только сменить общий пароль и сломать всем сразу.

### Реализация

Один новый эндпоинт:

```
POST /api/auth/agent-token
Authorization: Bearer <обычный токен>
```

Возвращает JWT, у которого `sub` — **тот же userId человека**, `groups` — `["USER","AGENT"]` без `ADMIN`, `exp` — 48 часов.

```java
@ApplicationScoped
public class JwtTokenProvider {

    public String generate(UserEntity user) {
        return build(user, groupsFor(user), lifespanFor(user));
    }

    /** Токен для ИИ-агента: тот же пользователь, урезанные группы, длинный срок. */
    public String generateAgentToken(UserEntity user) {
        return build(user, Set.of("USER", "AGENT"),      // ADMIN не попадает никогда
                     Duration.ofHours(48).toSeconds());
    }

    private String build(UserEntity user, Set<String> groups, long lifespanSeconds) {
        var now = Instant.now();
        return Jwt.issuer("taskmind")
                  .audience("taskmind-api")
                  .subject(String.valueOf(user.id))
                  .groups(groups)
                  .claim("username", user.username)
                  .jwtId(UUID.randomUUID().toString())
                  .issuedAt(now)
                  .expiresAt(now.plusSeconds(lifespanSeconds))
                  .sign();
    }

    private long lifespanFor(UserEntity user) {
        return user.isAdmin
            ? Duration.ofHours(2).toSeconds()     // как сейчас
            : Duration.ofHours(8).toSeconds();    // рабочий день
    }

    private Set<String> groupsFor(UserEntity user) {
        var groups = new HashSet<>(Set.of("USER"));
        if (user.isAdmin) groups.add("ADMIN");
        return groups;
    }
}
```

`.expiresAt(...)` теперь выставляется явно, поэтому `smallrye.jwt.new-token.lifespan` перестаёт влиять на результат. Строку из `application.properties` можно оставить как запасное значение или убрать, чтобы не вводить в заблуждение.

**`AGENT` добавляется к `USER`, а не заменяет его.** Если где-то стоит `@RolesAllowed("USER")`, замена группы сломает агенту доступ ко всему. Добавление же позволяет при желании закрыть отдельные эндпоинты через `@RolesAllowed` и не трогать остальные.

### Ограничение прав агента

Одно условие в `PermissionService`, никаких новых сущностей:

```java
private static final Set<Action> AGENT_FORBIDDEN = Set.of(
    Action.TASK_DELETE, Action.PROJECT_DELETE, Action.COMMENT_DELETE,
    Action.MEMBER_REMOVE, Action.ROLE_CHANGE
);

public void require(Integer projectId, Action action) {
    if (identity.hasRole("AGENT") && AGENT_FORBIDDEN.contains(action)) {
        throw new ForbiddenException(
            "Агент не выполняет удаление. Сделайте это вручную.");
    }
    // дальше обычная проверка проектной роли
}
```

Текст ошибки важен: модель передаст его человеку, и тот поймёт, что делать.

### Что это даёт

- **Журнал точен.** `sub` — это человек, значит видно «Дмитрий (через агента) сменил статус». Кто дал команду — понятно всегда.
- **Права ровно человека, минус разрушительное.** Синхронизировать ничего не надо: агент видит те же проекты, что и его хозяин, автоматически, и теряет доступ вместе с ним.
- **Никаких лишних сущностей.** Ни колонки `is_agent`, ни учётной записи `taskmind-agent`, ни таблицы токенов.
- **Администратор не становится администратором через агента.** `ADMIN` в агентский токен не попадает по построению, поэтому `/api/admin/users` и `/config/ai` агенту недоступны, даже если токен выпустил админ.
- **Отзыв личный.** Смена пароля ломает только вашего агента, а не общий доступ команды.
- **Срок дифференцирован.** Админ — 2 часа, обычный пользователь — 8 (рабочий день вместо трёх логинов в день), агент — 48 (кратно двум суткам, обновление не приходится на утро понедельника).

Почему срок вообще различается: claim `groups` — единственное, что в токене устаревает. Проектные роли берутся из базы и меняются мгновенно, а `ADMIN` застревает до конца срока. Под ним лежат удаление пользователей, `PUT /api/admin/users/{id}/status`, `GET /config/ai` (внутренний URL Ollama и абсолютный путь к каталогу проектов) и `POST /api/projects`. При двух часах снятие `isAdmin` действует быстро, при сорока восьми — двое суток. Поэтому админ на коротком сроке, а агент — на длинном, но без `ADMIN`.

### Как это выглядит для человека

В профиле появляется блок:

```
Доступ для ИИ-агента

Токен даёт вашему ИИ-помощнику право читать и изменять задачи
в ваших проектах. Удалять он ничего не может.

[ Создать токен на 48 часов ]

Активен до 9 сентября, 14:20
```

Дмитрий нажимает кнопку, копирует токен в настройки Claude или Cursor и говорит: «посмотри задачу 2, обнови резюме». Анна делает то же со своим токеном. В журнале задачи видно, кто из них что запросил.

Через двое суток токен истекает, агент получает понятную ошибку, человек нажимает кнопку ещё раз. Пятнадцать секунд раз в два дня.

### Мелочь в ответе логина

`AuthResponse.roles` возвращает `["USER"]`, хотя в токене `groups` содержит `["USER","ADMIN"]`. Клиент по ответу логина не может понять, что пользователь администратор, и вынужден либо разбирать JWT, либо звать `/api/users/me`. Стоит привести `roles` в соответствие с `groups` — иначе экран `/admin` придётся прятать по косвенным признакам.

### Если понадобится отзыв

**Денилист** (от англ. denylist, «список запрета») — список отозванных токенов, раньше это называли чёрным списком. У каждого вашего токена уже есть `jti` — уникальный идентификатор, вы его видели в payload. Если токен нужно отключить досрочно, его `jti` записывается в таблицу, а фильтр при каждом запросе проверяет, нет ли идентификатора в списке.

```sql
CREATE TABLE revoked_token (
    jti        VARCHAR(36) PRIMARY KEY,
    revoked_at TIMESTAMP NOT NULL,
    expires_at TIMESTAMP NOT NULL   -- для очистки: строки старше exp не нужны
);
```

В таблице лежат только отозванные токены, а их обычно ноль. Обычный запрос проверяет пустую таблицу по первичному ключу, то есть почти бесплатно.

**Заранее делать не нужно.** При сроке в 48 часов утёкший токен умрёт сам, а личный агентский токен обнуляется сменой пароля владельца.

### Когда 48 часов перестанут работать

Один сценарий стоит держать в голове. Такой срок предполагает, что раз в двое суток человек рядом и нажмёт кнопку. Для интерактивной работы («посмотри задачу 2, обнови резюме, переведи в готово») человек присутствует всегда.

Сломается это в день, когда захочется агента **без человека**: ночной прогон, cron, реакция на события. Тогда «кто дал команду» действительно нет, привязка токена к человеку теряет смысл, и вот там отдельная учётная запись со своей проектной ролью станет правильной. Появится соблазн положить в конфиг логин и пароль, чтобы скрипт логинился сам — это строго хуже: пароль не истекает никогда, даёт полный доступ к учётке и позволяет сменить сам себя.

**Признак, что момент настал:** вы пишете скрипт, который вызывает `/api/auth/login`. Пока такого скрипта нет — текущая схема правильная. Когда появится, возвращайтесь к денилисту на `jti` или к отдельной служебной учётке.


## 1.4 Урезанная спека для агента

36 эндпоинтов — много для модели. Половина ей не нужна: администрирование пользователей, конфигурация, отладочные ручки, загрузка файлов.

Отдавайте отдельную спеку по `/api/agent/openapi.json` — только то, с чем агент действительно работает:

| Операция | Зачем агенту |
|---|---|
| `POST /api/find` | найти задачи |
| `GET /api/tasks/{id}` | прочитать задачу |
| `GET /api/tasks/{id}/comments` | прочитать обсуждение |
| `PUT /api/tasks/{id}/summary` | записать резюме |
| `POST /api/tasks/{id}/comments` | оставить комментарий |
| `PATCH /api/tasks/{id}` | сменить статус, исполнителя, срок |
| `GET /api/project-statuses/project/{id}` | узнать допустимые статусы |
| `GET /api/projects` | список проектов |
| `POST /api/tasks/{id}/time` | списать время |

Девять операций вместо тридцати шести. Модель не путается, ответы точнее, расход токенов меньше.

Реализуется фильтром по тегам OpenAPI или статическим JSON, собираемым из основной спеки в тесте, чтобы он не устаревал.

## 1.5 Как это выглядит в работе

Дмитрий один раз нажал в профиле «Создать токен на 48 часов» и вставил его в настройки своего Claude. Токен выпущен на самого Дмитрия: `sub` — его `userId`, `groups` — `["USER","AGENT"]`.

Дальше он говорит агенту: **«Посмотри задачу 2 и обнови резюме».**

```
GET /api/tasks/2
Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9...
```

```json
{
  "id": 2, "title": "Вынести парсинг манифеста в отдельный сервис",
  "status": "В работе", "description": "Сейчас чтение манифеста живёт внутри...",
  "summary": null, "version": 4
}
```

```
GET /api/tasks/2/comments
```

Агент читает четыре комментария, замечает решение о переносе релиза и требование к старым пакетам, составляет текст и записывает:

```
PUT /api/tasks/2/summary
Content-Type: application/json

{ "summary": "Парсинг манифеста отделяется от проверки подписи: разбор
остаётся в отдельном сервисе, валидация уходит в фильтр. Парсер должен
корректно обрабатывать старые пакеты без поля schema. Работа идёт
в ветке feature/manifest-split. Релиз перенесён на 20 сентября." }
```

**«Переведи её в готово».**

```
GET /api/project-statuses/project/1        → узнать точные названия статусов
PATCH /api/tasks/2
X-Expected-Version: 4

{ "statusId": 5 }
```

Никакого кода на стороне бэкенда для этого писать не нужно.

### Понятная ошибка при истечении токена

```json
{ "message": "Срок действия токена истёк. Получите новый через POST /api/auth/login" }
```

Модель передаст этот текст человеку, и он поймёт, что случилось, вместо загадочного `401` в логах клиента.

# Вариант 2 — MCP (на будущее)

Более правильный путь в долгой перспективе, но требует нового расширения. Имеет смысл, когда захочется подключать агентов в один клик, без ручной настройки OpenAPI-инструментов.

## 2.1 Расширение

`quarkus-mcp-server`, версия 1.13.0, статус **stable**, поддерживают Red Hat и IBM, минимум Java 17. Реализована спецификация MCP 2025-11-25.

```xml
<dependency>
    <groupId>io.quarkiverse.mcp</groupId>
    <artifactId>quarkus-mcp-server-http</artifactId>
    <version>${quarkus-mcp-server-version}</version>
</dependency>
```

Транспорты: STDIO, Streamable HTTP (предпочтительный), SSE (устарел) и WebSocket. Интеграция с Quarkus Security для аутентификации и авторизации, полная поддержка CDI, Dev UI для проверки инструментов из браузера, журнал JSON-RPC-сообщений в разработке и библиотека `McpAssured` для тестов всех транспортов.

## 2.2 Код

Вся интеграция — аннотированные методы CDI-бина:

```java
public class TaskTools {

    @Inject TaskService tasks;
    @Inject ProjectStatusService statuses;

    @Tool(description = "Прочитать задачу по номеру. Возвращает заголовок, "
                      + "описание, статус, исполнителя, сроки и резюме.")
    TaskResponse getTask(
        @ToolArg(description = "Числовой номер задачи") Integer id) {
        return tasks.get(id);
    }

    @Tool(description = "Записать краткое резюме задачи: 2-4 предложения "
                      + "с решениями, сроками и ограничениями.")
    String setSummary(
        @ToolArg(description = "Номер задачи") Integer id,
        @ToolArg(description = "Текст резюме") String summary) {
        tasks.updateSummary(id, summary);
        return "Резюме обновлено";
    }

    @Tool(description = "Список допустимых статусов проекта. "
                      + "Вызывать перед сменой статуса.")
    List<String> listStatuses(
        @ToolArg(description = "Номер проекта") Integer projectId) {
        return statuses.namesOf(projectId);
    }

    @Tool(description = "Сменить статус задачи на указанный.")
    String setStatus(
        @ToolArg(description = "Номер задачи") Integer id,
        @ToolArg(description = "Название статуса из listStatuses") String statusName) {
        return tasks.changeStatus(id, statusName);
    }
}
```

Аутентификация остаётся той же — тот же JWT агента через Quarkus Security.

## 2.3 Когда переходить

Когда вариант 1 заработает и станет понятно, каких инструментов агенту не хватает. Переезд дешёвый: методы `@Tool` — обёртки над теми же сервисами, что уже вызываются из REST-ресурсов.

# Общее для обоих вариантов

## 3.1 Идемпотентность

Агенты повторяют запросы при таймаутах. Смена статуса дважды безвредна, второй одинаковый комментарий — мусор. Принимайте `Idempotency-Key` на `POST` комментариев:

```java
@POST
@Path("/{taskId}/comments")
public Response addComment(
    @PathParam("taskId") Integer taskId,
    @HeaderParam("Idempotency-Key") String idempotencyKey,
    CommentRequest request) {

    if (idempotencyKey != null) {
        var existing = comments.findByIdempotencyKey(idempotencyKey);
        if (existing.isPresent()) return Response.ok(existing.get()).build();
    }
    ...
}
```

## 3.2 Разделение действий

В README проекта записано: деструктивные операции не выполняются без явного подтверждения человека, при сомнении надо логировать, спрашивать или предлагать.

Нюанс: человек, сказавший «закрой задачу 2», — это **и есть** явное подтверждение. Правило нарушается не когда агент выполняет прямую команду, а когда он решает сам: «вижу, работа закончена, закрою». Разница в том, кто принял решение.

| Агент делает сам | Агент предлагает, человек подтверждает |
|---|---|
| читать задачи и комментарии | удаление чего угодно |
| писать резюме | смена исполнителя |
| добавлять комментарии | закрытие задачи по своей инициативе |
| менять статус по прямой команде | массовые операции |
| списывать время по команде | изменение прав и участников |

Для второй группы агент возвращает не результат, а описание намерения: «Готов закрыть задачу 2. Подтвердите». Модель покажет это человеку.

Технически это обеспечивается проверкой `AGENT_FORBIDDEN` в `PermissionService` (см. §1.3): удаление не пройдёт, даже если модель решит попробовать, и человек получит внятное объяснение вместо голого `403`.

## 3.3 Ограничение частоты

Агент в цикле способен положить API. Простейшая защита — счётчик на пользователя:

```properties
taskmind.api.rate-limit.per-user-per-minute=120
```

При превышении — `429` с заголовком `Retry-After`. Модели корректно обрабатывают этот код.

## 3.4 Пометка действий агента

Токен агента выпущен на человека, поэтому `sub` у агентского и обычного запроса одинаковый. Различить их можно только по группе `AGENT` **в момент запроса** — значит признак надо записать тогда же, иначе потом не восстановить.

### Где ловить признак

Главное решение — не «какая колонка», а где брать флаг. Соблазн протащить `boolean isAgent` параметром через `TaskService.changeStatus(...)` → `ActivityService.record(...)` заканчивается тем, что параметр появляется в двадцати сигнатурах и в половине из них его забывают передать.

Правильное место — request scope, один раз на запрос:

```java
@RequestScoped
public class CurrentActor {

    @Inject SecurityIdentity identity;
    @Inject JsonWebToken jwt;

    public Integer userId()    { return Integer.valueOf(jwt.getSubject()); }
    public boolean isAgent()   { return identity.hasRole("AGENT"); }
    public String  sessionId() { return jwt.getClaim(Claims.jti); }
}
```

`ActivityService` инжектит `CurrentActor` и заполняет поля сам. Ни один вызывающий код не меняется.

### Три способа хранения

| | Колонка `actor_type` | Ключ в `details` | Отдельный `actionType` |
|---|---|---|---|
| Миграция | нужна | не нужна | не нужна |
| Фильтр «скрыть агента» | индекс, быстро | перебор JSON | по списку типов |
| Существующие рендереры | не трогаются | не трогаются | **ломаются все** |
| Размер перечисления `actionType` | как есть | как есть | удваивается |
| Читаемость в БД | явная | спрятано в объекте | явная |

Третий вариант — `TASK_STATUS_CHANGED_BY_AGENT` рядом с `TASK_STATUS_CHANGED` — отбрасывается сразу. Он удваивает перечисление, ломает все существующие обработчики на фронтенде и смешивает **что произошло** с **кто это сделал**. Это два независимых измерения, их нельзя складывать в одно поле.

### Рекомендуется: отдельная колонка

```sql
-- V{N}__activity_actor.sql
ALTER TABLE activity ADD COLUMN actor_type    VARCHAR(10) NOT NULL DEFAULT 'HUMAN';
ALTER TABLE activity ADD COLUMN actor_session VARCHAR(36) NULL;

CREATE INDEX idx_activity_actor ON activity (actor_type);
```

`DEFAULT 'HUMAN'` закрывает вопрос со старыми записями: всё, что было до внедрения агентов, действительно сделано людьми.

```java
@ApplicationScoped
public class ActivityService {

    @Inject CurrentActor actor;

    @Transactional
    public void record(Integer taskId, String actionType, Map<String, Object> details) {
        var a = new ActivityEntity();
        a.taskId       = taskId;
        a.userId       = actor.userId();
        a.actorType    = actor.isAgent() ? "AGENT" : "HUMAN";
        a.actorSession = actor.isAgent() ? actor.sessionId() : null;
        a.actionType   = actionType;
        a.details      = details;
        a.createdAt    = Instant.now();
        a.persist();
    }
}
```

`actor_session` — это `jti` токена. Даёт то, чего булев флаг не даст: **сгруппировать все действия одной агентской сессии**. Когда агент за минуту обновил резюме, добавил комментарий и сменил статус, в ленте это сворачивается в одну строку «Агент Дмитрия: 3 действия» вместо трёх записей. И при разборе «почему задача изменилась» видно, что это был один заход, а не три независимых.

Колонка стоит четыре байта индекса и один `NULL` у человеческих записей. Если сворачивание не понадобится — просто не используется.

### Дешёвая альтернатива без миграции

`ActivityResponse.details` — свободный объект, туда можно положить ключ без изменения схемы:

```java
if (actor.isAgent()) {
    details.put("via", "agent");
    details.put("session", actor.sessionId());
}
```

Работает сразу, ноль SQL. Плата: фильтр «скрыть действия агента» превращается в перебор JSON на стороне приложения, а в H2 запросы по JSON слабые. Для личного инструмента приемлемо, для команды из десяти человек с активным агентом начнёт тормозить.

Брать этот вариант стоит, только если хочется проверить идею за полчаса, а колонку добавить потом.

### Как показывать

Пометка идёт **рядом с именем человека, а не вместо него**:

```
👤 Дмитрий Ковтун  ⚡через агента     сменил статус на «Готово»   2 ч назад
👤 Дмитрий Ковтун                     добавил комментарий          3 ч назад
```

Не «Агент» отдельной сущностью — иначе теряется ровно то, ради чего токен привязан к человеку.

```vue
<UUser :name="actor.fullName" :avatar="{ src: actor.avatarUrl }" size="xs">
  <template #description>
    <UBadge v-if="item.actorType === 'AGENT'" size="xs" variant="soft"
            color="secondary" icon="i-lucide-sparkles">
      через агента
    </UBadge>
  </template>
</UUser>
```

Цвет — `secondary` (светло-зелёный `sprout`), не `primary`. Пометка информирующая, а не тревожная: агент действовал по команде человека, ничего подозрительного не произошло.

Плюс переключатель над лентой:

```
Активность                        [ ] Скрыть действия агента
```

Он понадобится быстрее, чем кажется: агент, обновляющий резюме после каждого комментария, за неделю забьёт ленту.

### Что стоит пометить сверх журнала

**Комментарии — обязательно.** Это важнее журнала активности: комментарии люди читают, а журнал нет. Комментарий, написанный моделью, должен быть отличим от написанного Дмитрием, иначе через месяц никто не поймёт, чья это была мысль.

```sql
ALTER TABLE comments ADD COLUMN actor_type VARCHAR(10) NOT NULL DEFAULT 'HUMAN';
```

В `CommentResponse` уже есть `visibility` со значением `SYSTEM`, но это не то же самое: системный комментарий пишет сама программа, агентский пишет модель от имени человека. Разные вещи, смешивать не стоит.

**`summary` помечать не нужно** — там уже есть `summary_source: AI | MANUAL`. Дублировать не надо.

**Задачу и её поля не помечать.** `createdBy` и `updatedBy` остаются человеком: он владелец действия, агент лишь инструмент. Способ фиксируется в журнале, а не в самой сущности.

# План работ

**Вечер 1.** Заполнить `@Operation` и `@Parameter` для девяти агентских эндпоинтов. Самая важная часть: описания заменяют промпты.

**Вечер 2.** `generateAgentToken()` в `JwtTokenProvider`, эндпоинт `POST /api/auth/agent-token`, набор `AGENT_FORBIDDEN` в `PermissionService`, блок «Доступ для ИИ-агента» в профиле. Заодно развести сроки: админ 2 часа, обычный пользователь 8. Привести `AuthResponse.roles` в соответствие с `groups`.

Миграций на этом вечере нет — ни одной новой таблицы и ни одной новой колонки.

**Вечер 3.** Урезанная спека `/api/agent/openapi.json` плюс тест, что она не разошлась с основной. Подключить агента, попробовать вживую: «посмотри задачу 2 и обнови резюме».

**Вечер 4.** `CurrentActor`, колонки `actor_type` и `actor_session` в `activity`, `actor_type` в `comments`, бейдж «через агента» в ленте и в комментариях, переключатель «Скрыть действия агента» (§3.4).

**Дальше.** `Idempotency-Key`, ограничение частоты. MCP — когда станет ясно, чего не хватает. Денилист на `jti` и отдельная служебная учётка — только если появится агент, работающий без человека рядом.

# Приложение: инцидент с приватным ключом

**Статус: закрыто, коммит `c33741e`.**

`privateKey.pem` лежал в `META-INF/resources/`. По документации Quarkus это веб-корень приложения: чтобы отдавать статические ресурсы из jar, их кладут именно туда. Соответственно `GET /privateKey.pem` возвращал `200 OK` и тело ключа размером 1732 байта — без авторизации, любому.

Последствие: обладатель ключа подписывает себе токен с `sub` = любой `userId` и `groups: ["USER","ADMIN"]`. Проверка проходит, потому что подпись валидна.

Отягчающее обстоятельство: скомпрометированную пару ключей уже приходилось вычищать из истории git ранее.

**Что сделано:** ключ перенесён за пределы `META-INF/resources`, сгенерирована новая пара, подпись и проверка подтверждены на живом сервере (`GET /privateKey.pem` → `404`, `POST /api/auth/login` → валидный RS256-токен).

**Что стоит закрепить:**

1. Тест `StaticResourceTest`, фиксирующий `404` на `/privateKey.pem` — по духу тот же `OpenApiSpecTest`: свойство проверяется автоматически, а не держится в памяти.
2. Для прода вынести приватный ключ за пределы артефакта — путь к файлу или переменная окружения, а не ресурс внутри jar.
3. `publicKey.pem` может лежать где угодно, он публичный по определению.

Урок общий: в `META-INF/resources` попадает только то, что вы сознательно хотите раздавать по HTTP. Всё остальное — в корень `src/main/resources` или вовне.
