# ANotes

Фронтенд менеджера задач ANotes: Vue 3 + TypeScript + Vite + Nuxt UI (v4, Vue‑режим) + Pinia + vue-router.
    
API-контракт — `openapi5.yaml` (Quarkus/quarkus-smallrye-openapi, JWT через `Authorization: Bearer`). Дизайн-система и карта экранов — `taskmanager-spec.md`; там, где спецификация расходится с реальным API (нет priority, key, тегов-как-сущности, ролей и т.д.), приоритет отдан API.

## Запуск

Node ≥ 20.19 (или ≥ 22.12) — как требуют Vite 8 и Nuxt UI 4 (`engines` в `package.json`).

```bash
npm install
npm run dev
```

Дев-сервер проксирует `/api` на `http://localhost:8080` (см. `vite.config.ts`) — там должен быть поднят бэкенд из `openapi5.yaml`.

## Скрипты

- `npm run dev` — дев-сервер
- `npm run build` — сборка (`vite build`, затем `vue-tsc -b`)
- `npm run type-check` — только проверка типов
- `npm run preview` — предпросмотр собранного `dist`

## Адрес бэкенда

По умолчанию клиент ходит на `/api` **относительно своего же домена** — в разработке это подхватывает прокси `vite.config.ts` (`server.proxy['/api']`, сейчас нацелен на `http://127.0.0.1:8080`), в проде это должен обеспечить общий реверс-прокси перед фронтендом и бэкендом. Никакого адреса зашивать не нужно, пока фронт и бэк живут на одном домене.

Если бэкенд будет на **другом** домене (раздельный деплой) — задайте `VITE_API_URL` в `.env.production.local` (см. `.env.example`; файл не в git — шаблон Vite `*.local` уже в `.gitignore`, реальный адрес бэкенда — деплойная информация, а не то, что стоит коммитить в репозиторий):

```
VITE_API_URL=https://api.example.com
```

Дальше `npm run build` подставит этот адрес во все запросы (`src/api/http.ts` экспортирует `API_ORIGIN` — читают его же `files.ts`, `wikiFiles.ts`, `auth.ts` и раздел `/agent`, у всех иначе были свои прямые `fetch('/api/...')` в обход общей обёртки). Правки кода не нужны. Бэкенду в этом случае понадобится CORS на указанный origin (сессия — JWT в заголовке, не cookie, поэтому `credentials` в CORS не нужны).

Демо-режим (`VITE_DEMO=true`, см. `.env.demo`) `VITE_API_URL` не читает вовсе — там `http.ts` подменяет транспорт целиком (`src/api/demo/*`) ещё до того, как какой-либо адрес строится.

Если сайт открывается не в корне домена (например, `https://mysite.com/app/`, а не `https://mysite.com/`) — добавьте в тот же `.env.production.local` ещё и `VITE_BASE`:

```
VITE_API_URL=https://api.example.com
VITE_BASE=/app/
```

На своём корневом домене этого не нужно — по умолчанию `/` и так работает (см. `vite.config.ts`: `base: env.VITE_BASE || '/'`).

**Итого для нового сайта на своём домене с отдельным бэкендом:** создать `.env.production.local` с `VITE_API_URL` (и `VITE_BASE`, если не корень домена) → `npm run build` → раздать получившийся `dist/` любым статическим хостингом, отдельно от бэкенда.

## Что урезано относительно `taskmanager-spec.md`

API не поддерживает: приоритет задач, ключи вида `TSK-104`/`WEB`, отдельную сущность тегов (только `tags: string[]` на задаче/проекте), глобальные роли пользователей (есть `isAdmin`/`isActive` и per-project `roleId`), загрузку файла аватара (только `avatarUrl`-строка), удаление статусов проекта, архивацию проекта через API, админское создание пользователя (только само­регистрация `POST /api/auth/register`). Экраны `/tags`, `/people` соответствующим образом упрощены; страница `/tasks/:id` стала `/tasks/:projectId/:taskId`, так как задачи в API вложены в проект.

Признак админа (`auth.isAdmin`) берётся из `AuthResponse.roles` — сервер строит один список ролей и кладёт его и в JWT (`groups`), и в тело ответа логина, разъехаться они не могут. (Раньше тело у настоящих админов приходило пустым, и клиент домешивал роли из claim'ов JWT; после серверного фикса этот костыль убран.) На `/people` признак админа вообще не берётся из стора: экран стартует не-админом и пробит `GET /api/admin/users` — `200` → таблица администрирования (кнопка «Пользователь» заводит пользователя той же `/api/auth/register`, токен нового пользователя отбрасывается), `403` → каталог только для чтения.

Появилось в `openapi5.yaml` и подключено: `GET /api/roles` (справочник ролей — дропдаун в модалке участников), `PUT /api/users/me` и `PUT /api/users/me/password` (редактирование профиля и смена пароля на `/profile`), `PUT /api/project-statuses/{id}` + поле `isHidden` (модалка «Статусы» из меню строки проекта), `TaskResponse.version` + заголовок `X-Expected-Version` для `PATCH` задачи (оптимистичная блокировка с диалогом разрешения конфликта `409` на странице задачи).

Сохранение на странице задачи (`task_edit.md`) — пикеры правой панели (статус, исполнитель, срок, дата начала, оценка, теги) сохраняются сразу при выборе, оптимистично, запросы сериализуются; название и описание правятся явно через `InlineEdit` («Готово» пишет прямо на сервер), а незакоммиченный текст описания хранит черновик в `sessionStorage` — без липкой плашки, охранника ухода и `beforeunload`.

Отчёты по времени — страница `/reports` (`ReportsView.vue`) с тремя вкладками: по пользователю (`GET /api/reports/time`), по проекту (`GET /api/reports/time/project/{projectId}`) и по задаче (суммарное время + все списания из `GET /api/tasks/{taskId}/time` и `…/time/entries`, разбивка по авторам считается на клиенте). Выбранная вкладка, период и объект отчёта пишутся в query-параметры — ссылкой на конкретный отчёт можно поделиться. `403` (нет общего проекта с пользователем / не участник проекта) показывается как «Отчёт недоступен» прямо на странице.

Доступ для ИИ-агента (`ai.md`, вариант 1) — отдельный раздел `/agent` (`AgentAccessView.vue`; пункт в меню пользователя и в командной палитре). Всё для ручного подключения агента к задачам: **токен** (`POST /api/auth/agent-token` — второй JWT на того же пользователя, группы `USER`+`AGENT` без `ADMIN`, 48 часов, без рефреша; создать/показать/скопировать/пересоздать/удалить), **адреса** (`${origin}/api` и `${origin}/api/agent/openapi.json`) с копированием и кнопкой «Скачать» (`fetchAgentOpenApi` — авторизованный `fetch`, т.к. URL под `bearerAuth` и в браузере не открывается), готовый **системный промпт**, **примеры задач**, список «может / не может» и блок **«Всё одним куском»** — токен + адреса + правила одним markdown-текстом с кнопками «Скопировать всё» / «Скачать .md» (в превью токен скрыт, в копии и файле — полный). Токен хранится только в `localStorage` (`auth.agentToken`) — приложение им никуда не ходит, это учётные данные для вашего ИИ-клиента. «Удалить» забывает токен локально (отзыва на сервере нет). В профиле осталась строка-статус со ссылкой в раздел. MCP (вариант 2) не делаем — на бэкенде его нет.

Действия агента помечаются (`ai.md` §3.4): `CommentResponse.actorType` и `ActivityResponse.actorType`/`.actorSession` (`HUMAN`/`AGENT`). Бейдж `AgentBadge.vue` («через агента») рисуется рядом с именем автора в списке комментариев и в карточке «Активность» на странице задачи; там же переключатель «Скрыть действия агента». Автором действия остаётся человек — агент лишь инструмент.

Эпики и задачи (`parent_task.md`) — иерархия работы через **вид сущности**, а не свободное родительство. `TaskResponse.taskType` = `TASK | EPIC`; у эпика нет исполнителя, своего статуса и списания времени (`assignedUserId`/`statusId` = `null`), прогресс (`childTotal`/`childDone`/`epicClosed`) считает сервер по флагу `isClosed` статусов дочерних задач. Единственная развилка кода — `isEpic()` (`src/utils/taskType.ts`), страница общая (`/tasks/:projectId/:taskId`), внутри разный набор блоков. Страница эпика: блок прогресса вместо селекторов статуса/исполнителя (`EpicProgress.vue`), список задач с чекбоксами (`EpicTaskList.vue` — чекбокс переключает статус между стартовым `isDefault` и закрывающим `isClosed` без открытия задачи, оптимистично, с `X-Expected-Version` задачи; «+ Задача» открывает модалку с зафиксированным эпиком), «Списано» = сумма по задачам без формы, кнопка «Преобразовать в задачу», удаление с выбором `?children=detach|delete`. На странице обычной задачи — селектор «Эпик» (`PUT /api/tasks/{id}/parent`, отдельная ручка: PATCH не различает присланный `null`) и хлебная крошка к родителю. Модалка создания: первое поле «Вид» (Задача/Эпик; у эпика показывается пояснение). Список `/tasks`: фильтр `?type=task|epic` (`FindTasksRequest.taskType`), эпики в таблице с иконкой `i-lucide-package` и бейджем прогресса вместо статуса. Новые ручки: `GET /api/epics/{id}/tasks`, `GET /api/projects/{id}/epics` (кэш `dictionaries.epicsByProject`), `PUT /api/tasks/{id}/convert`. Счётчики задач проекта считаются с `taskType: 'TASK'` — эпик не единица работы.

Доска по статусам (`status_view.md`) — режим `?view=board` в том же переключателе вида на `/tasks`. Колонки — статусы выбранного проекта (по `statusOrder`, скрытые не рисуются), карточки — задачи в колонке своего `statusId`; эпики на доску не попадают (`statusId = null`). Данные — все задачи проекта разом, как в режиме «по эпикам»; раскладку по колонкам и фильтрацию делает `useStatusBoard`. Перетаскивание карточки между колонками — нативный HTML5 drag, оптимистично с откатом; `X-Expected-Version` берётся у карточки, `409` → карточка возвращается на место + перезапрос. `StatusBoard.vue` / `BoardCard.vue`. Серверных изменений не потребовалось.

Уведомления без почты (`notifications.md`, §1 «Колокольчик») — `NotificationBell.vue` в шапке: счётчик непрочитанных опрашивает `GET /api/notifications/count` раз в ~45 с (`stores/notifications.ts`), список — `UPopover`, подгружается при открытии. Типы `MENTION | ASSIGNED | COMMENT | STATUS_CHANGED`; клик ведёт на задачу (`taskId` → `projectId` через `POST /api/find`). Настройки по типу — карточка на `/profile`. SSE (`notifications.md` §2), Web Push (§3), мессенджер (§4), `DUE_SOON` по расписанию (§7) не делаем — на бэкенде их нет.

Упоминания `@username` в описании задачи и комментариях — `MentionTextarea.vue`: по `@` открывается список **участников проекта** (не `/api/users`), в текст попадает `@username`, при отображении — «@Имя». Сервер по факту упоминания создаёт уведомление `MENTION`. Значок ⓘ (`EditorHint.vue`) рядом с полем — подсказка по клавишам, упоминаниям и ссылка в справку.

Группировка `/tasks` по эпикам (`tasks_view.md`, целиком на клиенте) — режим `?view=epics` в переключателе вида. `useEpicGrouping` раскладывает задачи по `parentId`, заголовки и прогресс берёт из `dictionaries.epicsByProject` (дочерняя задача не несёт `childTotal` родителя, а фильтр «мои» вообще не возвращает эпики). Режим работает в пределах одного проекта и грузит **все** его задачи — `fetchAllProjectTasks` страницами по 200 (флага `grouped` в `/api/find` нет, серверных изменений не потребовалось). `EpicGroupHeader.vue` — сворачиваемый заголовок (`#id`, полоса прогресса при `childTotal > 1`, «· показана N» при частичной фильтрации). `useEpicCollapse` хранит в `sessionStorage` (по проекту) *развёрнутые* группы — по умолчанию всё свёрнуто: сначала видно структуру (заголовки эпиков с прогрессом), задачи разворачиваешь по месту. «Без эпика» всегда последняя. При выборе проекта с эпиками режим включается сам (если человек не переключил вручную). `Shift`+`←`/`→` — свернуть/развернуть все; у пустого эпика — ссылка «Добавить».

База знаний (вики) — модуль под проект, спецификация в `wiki.md`. Экраны: `/projects/:projectId/wiki[/:pageId]` (`WikiIndexView` — дерево на два уровня слева + чтение страницы справа, дерево внутри страницы, а не в каркасе — правило «боковой панели нет» не нарушено), `/projects/:projectId/wiki/new` и `/projects/:projectId/wiki/:pageId/edit` (`WikiEditView` — отдельный маршрут, автосохранение черновика в `sessionStorage`, заголовок `X-Expected-Version` шлётся всегда, конфликт `409` → диалог «перезагрузить/перезаписать»), `/projects/:projectId/wiki/:pageId/history` (`WikiHistoryView` — список ревизий + построчный diff на клиенте, «Восстановить версию» = сохранить старый снимок новой правкой). Ссылки в тексте: `[[Заголовок]]` — на страницу проекта (или «красная», если такой страницы нет), `#123` — на задачу. Точки входа: меню строки проекта на `/projects` («База знаний»), командная палитра, карточка «Документация» на странице задачи (`GET /api/tasks/{taskId}/wiki`).

Краткое описание страницы (`wiki_summary_client.md`): поле `summary` — одно предложение «о чём страница». Обязательно при создании (1..500), необязательно при правке (пустую строку не шлём — сервер её не примет, отсутствие ключа = «не менять»). У страниц, созданных до появления поля, `summary === null` — в форме правки мягкая подсказка добавить, сохранение не блокируется. В дереве навигации под каждым заголовком строка описания: своё описание (`summaryInferred: false`) — обычный muted; автопревью из начала текста (`summaryInferred: true`) — dimmed + курсив + подсказка «Автопревью». `POST /api/wiki/find` по `contentSearch` теперь матчит и по описанию; в командной палитре описание показывается сниппетом. Агенту (`/api/agent/openapi.json`) добавлены три операции вики **только на чтение** (дерево, страница, поиск) — правка вики агенту не выдаётся; отражено в списке «может / не может» на `/agent`.

Отличия от `wiki.md`: ссылки на задачи по числовому id (не `TSK-123`); перемещение страницы по дереву не поддерживается; `jsdiff` не подключается — свой LCS-differ в `src/utils/linediff.ts`.

Вложения страницы вики (`wiki_files_client.md`) — файлы и картинки в `content`, без собственной схемы ссылок: обычный `![подпись](/api/wiki/files/{storedName})`, чтобы текст оставался переносимым Markdown (копируется в другой редактор, экспортируется). Бэкенд уже реализован (`Wiki File Resource` в `openapi5.yaml`): `GET/POST /api/wiki/{pageId}/files`, `DELETE /api/wiki/files/{id}?force=`, `GET /api/wiki/files/{storedName}` (отдача файла, `isImage` — картинка вставляется inline, иначе только ссылка на скачивание). Ручка отдачи требует `Authorization`, обычный `<img src>`/`<a href>` его не пришлёт — поэтому `WikiMarkdown.vue` не получил новое расширение `marked` (стандартный `![]()` и так рендерится), а донагружает такие изображения авторизованным `fetch` и подменяет `src` на `blob:` (`useAuthorizedImages.ts`; сорванная загрузка → плейсхолдер «Изображение недоступно», а не пустое место). `WikiEditView.vue`: три равноценных способа положить файл — перетаскивание, вставка скриншота из буфера, кнопка в панели вложений (`useWikiFileDrop.ts` — плейсхолдер на месте курсора сразу, прогресс через `httpUpload()` в `http.ts`, XHR вместо `fetch`, который прогресс отправки не отдаёт). Прикреплять файлы можно только у уже сохранённой страницы — вложение привязано к `pageId`. `WikiAttachments.vue` — сворачиваемая панель (список, вставка ссылки повторно, удаление; `409` на удаление уже используемого файла → диалог подтверждения с `force=true`), используется и в редакторе, и в чтении (там — только список и скачивание).

Дорожная карта эпиков (`roadmap.md`) — временная шкала эпиков проекта, `/projects/:projectId/roadmap` (`RoadmapView.vue`), одна ручка `GET /api/projects/{projectId}/roadmap` (`src/api/roadmap.ts`). Одна полоса — один эпик от `startDate` до `dueDate` (effective: свои даты эпика либо выведенные по задачам — тогда `datesInferred`, полоса пунктиром); внешний прямоугольник — срок в приглушённом цвете состояния, внутренняя заливка — прогресс `childDone/childTotal` в насыщенном. Состояние (`NOT_STARTED|IN_PROGRESS|DONE|AT_RISK|OVERDUE`) и `childOverdue` считает сервер. Геометрия — `composables/useTimeScale.ts` (дата → % позиции, деления недели/месяцы/кварталы, `autoScale` по диапазону данных); переключатель масштаба зеркалится в `?scale=`. Линия «сегодня» через все строки; эпики без дат вообще — списком «Без сроков» под шкалой (не прячутся). `403` (не участник) и `400` (эпиков больше серверного предела) — inline-`EmptyState`. Точка входа — иконка-кнопка «Дорожная карта» в строке проекта на `/projects`, рядом с кнопкой вики (проектные экраны единообразны: `PageHeader` + ссылка «Назад к проектам», отдельной навигации по проекту в приложении нет). Отличия от `roadmap.md`: даты — epoch-ms (не `LocalDate`); поля `key` в `RoadmapItem` нет (`#id`); перетаскивания полос и своего пересчёта состояния на клиенте нет.

Вехи (`plan.md` §5) — контрольные точки по срокам, ось, ортогональная эпику: веха отвечает «к какому числу», собирает задачи (не эпики) из разных направлений. `src/api/milestones.ts`, кэш `dictionaries.milestonesByProject`. Экраны вложены в проект: `/projects/:projectId/milestones` (`MilestoneListView` — список по возрастанию срока, переключатель «Показать закрытые») и `/projects/:projectId/milestones/:milestoneId` (`MilestoneDetailView` — у каждой задачи показан её эпик, `⚠` если срок задачи позже срока вехи; «Закрыть веху» / «Открыть заново»; удаление трёхпутёвое — открепить / перенести в другую веху, задачи не удаляются). `dueDate` обязателен (epoch-ms). Состояние (`PLANNED|IN_PROGRESS|READY|AT_RISK|LATE|CLOSED`) и прогресс (`taskTotal/taskDone/taskOverdue`) считает сервер; `READY` (всё готово, но не закрыто) показывается баннером с кнопкой «Закрыть веху». Привязка задачи к вехе — `PUT /api/tasks/{taskId}/milestone` (`setTaskMilestone`), не PATCH; при создании — поле `milestoneId` в `TaskRequest`. Точки входа: иконка-ромб в строке `/projects`, селектор «Веха» на странице задачи и в `TaskFormModal`, ромбы вех на дорожной карте, фильтр «Веха» и режим «По вехам» в `/tasks` (`useMilestoneGrouping` / `MilestoneGroupHeader`). Ключа нет — `#id`; маршрут вложен в проект (в `plan.md` §5.1 плоский `/milestones/:id`).

Личная доска (`/dashboard`, `DashboardView.vue`) — сводка «назначено мне» через все проекты разом, без выбора одного из них (в отличие от `/tasks`). Один запрос `POST /api/find` (`assignedToMe: true`, без фильтра по статусу, лимит 500) несёт всё нужное — `projectId`/`milestoneId`/`milestoneTitle` на каждой строке, поэтому фильтры «Проект» и «Веха» строятся на клиенте из уже полученных задач, без дополнительных обращений к серверу. Открытые задачи разложены по срочности (`Просрочено` / `На этой неделе` / `Без срочности`) — не по статусу, потому что статусы per-project и единого набора колонок через разные проекты нет. Отдельным приглушённым и зачёркнутым блоком внизу — «Недавно закрыто»: задачи, уже закрытые, но обновлённые за последние 24 часа (`updatedAt` как приближение к «дате закрытия», которой в API нет). Пункт первый в верхнем меню и в командной палитре.

Таймер работы (`src/stores/workTimer.ts`) — секундомер целиком на клиенте, серверных изменений не потребовалось. Состояние (задача, накопленные секунды, момент старта текущего отрезка) хранится в `localStorage`, а не только в памяти — обновление страницы и переход между разделами его не сбрасывают; в API уходит только итог, одним уже существующим вызовом `POST /api/tasks/{taskId}/time` (`logTime()`, тот же, что у формы ручного ввода). Кнопка «Запустить таймер» — в карточке «Учёт времени» на странице задачи; пока он идёт, полоска под шапкой (`WorkTimerBar.vue`, смонтирован в `AppHeader.vue`) показывает название задачи, счётчик и паузу/стоп на **любой** странице, не только на странице своей задачи. Активен один таймер сразу: запуск другого, пока этот не остановлен, сначала ставит текущий на паузу и открывает форму записи/сброса (`WorkTimerLogModal.vue`, предзаполнена посчитанным временем) — без неё секунды потерялись бы молча при переключении между проектами. Отдельно — защита от забытого таймера: `localStorage` хранит именно момент старта, поэтому включённый в пятницу и не остановленный таймер после выходных при следующей загрузке страницы честно посчитает реальные часы простоя; если отсчёт превысил 8 часов, таймер замораживается и форма записи открывается сама, предзаполненная 8 часами вместо реальных — записать как есть, указать своё значение или сбросить.
