# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Frontend for **ANotes**, a task/project manager. Vue 3 + TypeScript + Vite + Nuxt UI v4 (Vue-only mode, not Nuxt) + Pinia + vue-router. No backend lives in this repo — it talks to a separate Java/Quarkus REST API over `/api`.

Two source-of-truth documents at the repo root drove this build and should be consulted before adding features:

- **`openapi5.yaml`** — the actual, generated API contract (`quarkus-smallrye-openapi`). This is authoritative. Never invent a request/response field that isn't in this file.
- **`taskmanager-spec.md`** — the design system, screen map, and UX behavior spec (in Russian). Authoritative for layout, components, copy tone, and interaction rules.

**When the two conflict, `openapi5.yaml` wins.** The spec describes a richer domain than the API actually implements (see "Where the API and spec diverge" below) — do not build UI against fields or endpoints the API doesn't have, even if the spec describes them.

## Commands

```bash
npm run dev          # Vite dev server, proxies /api -> http://localhost:8080 (see vite.config.ts)
npm run build         # vite build && vue-tsc -b  (type errors fail the build)
npm run type-check    # vue-tsc -b only
npm run preview       # preview the built dist/
```

There is no test suite and no lint/format config in this repo — don't assume `npm test` or `npm run lint` exist.

`npm run build` runs `vite build` **before** `vue-tsc`, deliberately: Nuxt UI's vite plugin generates `auto-imports.d.ts` and `components.d.ts` on first run, and `vue-tsc` needs those to exist to resolve globals like `useToast`, `UButton`, etc. Don't reorder this.

## Architecture

### Auto-imports — don't add explicit imports for Nuxt UI

Per `taskmanager-spec.md`, all Nuxt UI components (`UButton`, `UModal`, `UTable`, ...) and Nuxt UI composables (`useToast`, ...) are consumed via auto-import (`unplugin-vue-components` / `unplugin-auto-import`, wired through `@nuxt/ui/vite` in `vite.config.ts`). **Do not manually `import` these** — write `useToast()` or `<UButton>` directly and let the codegen handle it. The generated `auto-imports.d.ts` / `components.d.ts` at the repo root are gitignored; if types for a Nuxt UI symbol appear missing, run `npm run dev` or `npm run build` once to regenerate them before assuming something is broken.

Everything else (our own components, stores, api modules, utils) uses explicit `@/...` imports — the `@` alias maps to `src/` (declared in both `vite.config.ts` and the `paths` entry in `tsconfig.app.json`; keep both in sync if it ever changes).

### Theming — one file controls color

`src/theme.ts` exports `THEME.primary/secondary/neutral`, consumed by the `ui()` plugin options in `vite.config.ts`. The current palette (`violet` / `fuchsia` / `mauve`) comes from the Nuxt UI Theme generator (`ui.nuxt.com/theme`); all three are stock Tailwind v4 colors, so no custom `@theme` block is needed — `main.css` only defines `--font-sans/mono`. The rest of that generator export also lives in the repo: `--ui-radius: 0.5rem` + the `tokenShades` overrides (`--ui-bg`/`--ui-bg-muted`/`--ui-text-inverted` shifted onto `neutral-50/100`) + `letter-spacing: -0.01em` in `src/assets/css/main.css`, and the input `subtle` variant default in `vite.config.ts` under `ui:` (`input`/`inputNumber`/`textarea`/`select`/`selectMenu`/`inputMenu`/`inputTags`/`pinInput`). **Buttons are a three-tier system the user dictated (2026-09-08), all in violet:**
1. **Action buttons — `color="primary"` (stock `variant: solid`): violet fill, white text.** Every CTA carries `color="primary"`; a few that were `variant="soft"` (wiki "Изменить", profile "Открыть раздел", agent copy) were made solid. The generator's own `buttons: outline` was tried and rejected.
2. **Secondary / chrome buttons — `variant="outline" color="primary"`: violet border, no fill.** Modal "Отмена"/"Закрыть", `ConfirmDialog` cancel, header icons (hamburger/search/bell), every `⋯` trigger, filter "Сбросить", and the small row-action icons (file download/preview/upload, project row wiki/members/statuses icons, token reveal/copy). This replaced the old `variant="ghost" color="neutral"` on those.
3. **Destructive — `color="error"` / `"warning"`** (unchanged).

Still `variant="ghost" color="neutral"` on purpose: delete/remove icon buttons (`×` remove file / remove member, trash a time-entry, "Удалить" agent token) and the mobile-nav list in `AppHeader`. `variant="link"` text-links ("Прочитать все", wiki "Восстановить эту версию") and three `variant="soft" color="neutral"` buttons (regenerate token, "Скачать .md", epic "Открепить") were left as-is. **When adding a button: action → `color="primary"`; secondary → `variant="outline" color="primary"`; destructive → `color="error"`.** This whole theme is a deliberate departure from `taskmanager-spec.md`'s green (`moss`/`sprout`) design system. The generator's `icons: bootstrap` was **not** applied (would mean migrating every `i-lucide-*` ref). Templates must use semantic classes (`bg-primary`, `text-muted`, `border-default`, ...), never `bg-violet-500` directly — that's what keeps a theme swap to a one-line change in `theme.ts`.

### API layer (`src/api/`)

One file per OpenAPI resource group (`tasks.ts`, `projects.ts`, `admin.ts`, `comments.ts`, `files.ts`, `timeEntries.ts`, ...), each a thin set of functions wrapping `src/api/http.ts`. `http.ts` is a `fetch` wrapper (no axios, per the spec's hard constraint) that:

- attaches `Authorization: Bearer <token>` from the Pinia auth store,
- redirects to `/login` and clears the session on `401` (via `authStore.handleUnauthorized()`),
- throws `ApiError` (with `.status`/`.message`) on any non-2xx response.

`src/types/domain.ts` mirrors the OpenAPI `components/schemas` **exactly** — field names, optionality, and types should trace back to `openapi5.yaml`. Don't add convenience fields the API doesn't return.

One API module exists but isn't wired into any view yet: `discussion.ts` (Task Discussion Resource — threaded blocks with `BlockType`). Building UI for it is a legitimate follow-up, not a bug.

`timeReports.ts` **is** wired now — `/reports` (`ReportsView.vue`) has a 3-tab segmented control ("По пользователю" `GET /api/reports/time`, "По проекту" `GET /api/reports/time/project/{projectId}`, "По задаче" — client-side aggregate of `GET /api/tasks/{taskId}/time` + `/entries` by author, since those endpoints have no user breakdown). Tab/period/selection are mirrored to the URL query (`?tab=&year=&month=&user=|project=|task=`) so a report is a shareable link. Shared bits: `components/reports/PeriodControls.vue` (month `0` = whole year), `TimeReportBreakdown.vue` (+ `breakdown.ts` for the row type). `403` on a report is expected (no shared project with the target user / not a project member) and rendered as an inline "Отчёт недоступен", not a toast.

`wiki.ts` (Project/Task Wiki + Wiki resources) **is** wired now — the knowledge-base module, spec at `wiki.md`. Views: `WikiIndexView` (`/projects/:projectId/wiki[/:pageId]` — two-column tree + reader, per `wiki.md` §7.2 the tree lives *inside* the page so the "no sidebar" rule holds), `WikiEditView` (`.../wiki/new` and `.../wiki/:pageId/edit` — separate route, `sessionStorage` draft autosave, always sends `X-Expected-Version`, 409 → reload/overwrite dialog), `WikiHistoryView` (`.../wiki/:pageId/history` — revision list + client-side line diff via `src/utils/linediff.ts`, "restore" = PUT the old snapshot as a new version). `POST` create returns no body, so the new page's id is recovered by re-reading the tree and matching on the (project-unique) title. Tree cached in `dictionaries.wikiTreeByProject` (force-refresh after every mutation). `WikiMarkdown.vue` renders content with two inline `marked` extensions: `[[Page Title]]` → link (red "create" link if unresolved) and `#123` → task link. Task links target `/tasks/{projectId}/{id}` (there is **no** `/projects/{pid}/tasks/{id}` route); since task ids are global and the API has no get-task-by-id, `WikiMarkdown` resolves each `#id`'s real project + title via one `POST /api/find` (falls back to the current page's project until resolved). Entry points: `/projects` row menu ("База знаний"), command palette group, and a "Документация" card on `TaskDetailView` (`GET /api/tasks/{taskId}/wiki`). **Page `summary`** (`wiki_summary_client.md`, server merged): one-sentence "what this page is about" — `WikiPageRequest.summary` **required** on create (1..500, non-blank), `WikiPageUpdateRequest.summary` optional and the client sends it **only when non-blank** (empty string → 400, so an untouched/cleared field = omit the key = "keep"). `WikiPageResponse.summary` is `string | null` (null on pre-feature pages; `GET` never auto-previews). `WikiTreeNodeResponse` gained `summary: string | null` + `summaryInferred: boolean` (`true` = trimmed content preview, not an authored line; `null` = markdown-only content) — `WikiTree` renders it under each title (inferred → `italic text-dimmed` + "Автопревью" tooltip, null → "Без описания"). `WikiEditView` create form has a required "Краткое описание" `UTextarea` with a `/500` counter; edit form prefills it and shows a soft warning bar when the loaded page's `summary` was `null`. `WikiPageContent` shows it as a lead under the H1; `CommandPalette` wiki items carry it as `description`. `POST /api/wiki/find` `contentSearch` now matches `summary` too (no client change needed). The AI-agent OpenAPI (`/api/agent/openapi.json`) gained wiki **read** ops (tree/page/find) — `AgentAccessView` rules + can/can't lists updated; agents still cannot create or edit wiki pages.

`roadmap.ts` (Roadmap Resource) **is** wired now — the epic timeline, spec at `roadmap.md`. One view `RoadmapView.vue` at `/projects/:projectId/roadmap` (name `roadmap`, nested under the project like wiki — no top-level menu item), one call `GET /api/projects/{projectId}/roadmap` → `RoadmapResponse` (`{ rangeFrom, rangeTo, items, undated }`, all dates **epoch-ms**). One bar per epic from effective `startDate`→`dueDate` (own dates, else derived from children → `datesInferred` → dashed border); **outer rectangle = due window in a muted state color, inner fill = `childDone/childTotal` progress in a saturated color** (`roadmap.md` §4.4 — the one visual idea worth explaining). `state` (`NOT_STARTED|IN_PROGRESS|DONE|AT_RISK|OVERDUE`) and `childOverdue` are **server-computed** — no client re-derivation (`roadmap.md` §4.6). `RoadmapItem` has **no `key`** (`#id` shown) and no `projectId`. Geometry lives in `composables/useTimeScale.ts` (`posOf` date→%, `barStyle`, `ticks` for week/month/quarter, `autoScale(from,to)` picks the default granularity by span); the scale toggle mirrors to `?scale=`. "Today" line spans all rows (only when in range). Epics with no dates at all → "Без сроков" list under the chart (never hidden — `roadmap.md` §2.2). `403` (not a member) / `400` (too many epics) render as inline `EmptyState`. Entry point: a "Дорожная карта" icon-button (`i-lucide-calendar-range`) in the `/projects` row, next to the wiki button — same as how wiki is reached (project-scoped screens are `PageHeader` + "Назад к проектам" back-link, no in-app project-nav chrome exists). No bar drag, no virtualization (`roadmap.md` §4.6).

`milestones.ts` (Milestone / Project Milestone / Task Milestone resources) **is** wired now — the epic-orthogonal "к какому сроку" axis, spec at `plan.md` §5. A milestone is a point on the timeline (release/demo/deadline), collects `TASK`s from *different* epics (never epics — `chk_epic_no_milestone`), has no assignee/own status, `dueDate` is **required** (epoch-ms — `plan.md` deviates from its own `DATE`). `MilestoneState` (`PLANNED|IN_PROGRESS|READY|AT_RISK|LATE|CLOSED`) + progress (`taskTotal/taskDone/taskOverdue`) are **server-computed**; only `OPEN`/`CLOSED` is stored. `READY` ≠ `CLOSED` — all tasks done but not closed by a human (a banner on the page offers to close; the system never auto-closes, per README's principle). Views nested under the project like wiki/roadmap: `MilestoneListView` (`/projects/:projectId/milestones` — list + "показать закрытые" toggle), `MilestoneDetailView` (`.../milestones/:milestoneId` — shows **each task's epic** in a column, `⚠` on tasks whose own `dueDate` is past the milestone's, close/reopen, 3-way delete: детач/перенос — **tasks are never deleted**, `plan.md` §4.4). `MilestoneFormModal` (create/edit, `X-Expected-Version` on edit), `MilestoneTaskList` ("Добавить" pulls project tasks via `POST /api/find` `noMilestone:true`, checkbox flips a task between the project's `isDefault`/`isClosed` status like `EpicTaskList`, "×" detaches). Binding a task to a milestone is **`PUT /api/tasks/{taskId}/milestone`** (`setTaskMilestone` in `milestones.ts`) — **not** PATCH (`TaskUpdateRequest` has no `milestoneId`); `TaskRequest` (create) **does**. `TaskResponse` gained `milestoneId`/`milestoneTitle`/`milestoneDueDate` + `milestoneReady` (true = this edit closed the last open task). Cache: `dictionaries.milestonesByProject` (state=all, filter `!== 'CLOSED'` for "open"), force-refresh after every mutation. Entry points: `i-lucide-diamond` icon-button in the `/projects` row (next to roadmap/wiki), a "Веха" selector on `TaskDetailView` + `TaskFormModal`, diamond markers on `RoadmapView` (`plan.md` §5.5), and a "Веха" filter + a **"По вехам"** view mode in `/tasks` (`plan.md` §5.6 — `useMilestoneGrouping` / `MilestoneGroupHeader`, collapse via `useEpicCollapse(pid, 'milestoneExpanded')`). No key (`#id`). `plan.md` §5.1's flat `/milestones/:id` lost to project nesting, same as wiki/roadmap.

### State (`src/stores/`)

- `stores/auth.ts` — JWT token + roles (persisted to `localStorage`, not domain data so this doesn't violate the spec's "no localStorage for domain data" rule) and the current `UserProfile`. Also owns `handleUnauthorized()`/`logout()`, both of which redirect via the router. `isAdmin` is derived straight from `roles` = `AuthResponse.roles` — the server builds one role list and puts it in both the JWT (`groups` claim) and the login response body (`AuthService`), so they can't diverge. (Earlier the body came back empty for real admins and the client merged in the JWT's own claims via `src/utils/jwt.ts`; that `claimsRoles`/`effectiveRoles` workaround was removed once the server was fixed — `jwt.ts` stays, only for `jwtExpiresAt`.) `PeopleListView` doesn't read `isAdmin` at all — starts non-admin and probes `GET /api/admin/users` (200 → admin table, 403 → read-only catalog). `login`/`register` call `src/api/auth.ts`. Also holds `agentToken` (+ `setAgentToken`/`clearAgentToken`, key `taskmind.agentToken`, cleared on `logout`/401) — the AI-agent JWT from `POST /api/auth/agent-token`, kept only so `/profile` can show its expiry and re-copy it; never sent by `http.ts` (that always uses the human `token`).
- `stores/dictionaries.ts` — shared cache for projects, users, roles (`RoleResponse[]` from `GET /api/roles`), per-project statuses (`ProjectStatusResponse[]`, keyed by project id — statuses are **per-project**, not a global enum, unlike the spec's original `TaskStatus` union), and project appearance (colors/icons presets).

`stores/auth.ts` and `src/router/index.ts` import each other (guard calls `useAuthStore()`, store calls `router.push()` on logout/401). This is intentional and safe — both only touch the other module inside function bodies, never at module-eval time. Don't "fix" this into one file.

### Global UI singletons (`src/composables/useGlobalUi.ts`)

Plain module-level refs (not a Pinia store) used to coordinate cross-component UI state that doesn't belong in any one component's tree: `commandPaletteOpen`, `createTaskModalOpen`, `focusSearchSignal`, and `tasksVersion` (bumped after any task mutation so open lists know to refetch — check for a `watch(tasksVersion, ...)` when adding a new view that lists tasks). `useShortcuts.ts` wires the global keyboard shortcuts (`⌘/Ctrl+K`, `C`, `/`, `Esc`) into these same refs.

### Routing

`/tasks/:projectId/:taskId`, not `/tasks/:id` — tasks are nested resources in the API (`GET /api/projects/{projectId}/tasks/{taskId}`), so a task can't be fetched by id alone. Keep this in mind if you're tempted to "simplify" the route.

Wiki routes are also nested under the project (`/projects/:projectId/wiki/...`) even though `GET /api/wiki/{pageId}` works by id alone — the tree, "new page", and `[[link]]` resolution all need `projectId` in hand, so keeping it in the URL is simpler than deriving it. This diverges from `wiki.md` §7.1's flat `/wiki/:id`; the nesting won.

### Confirm dialogs

`useConfirm()` (`src/composables/useConfirm.ts`) returns a promise-based `confirm({ title, description, danger })`. It drives a single globally-mounted `<ConfirmDialog />` (mounted once in `App.vue`) via shared reactive state — don't instantiate `ConfirmDialog` per-component, just call `useConfirm().confirm(...)`.

## Where the API and spec diverge

`taskmanager-spec.md` was written somewhat aspirationally; several things it describes don't exist in `openapi5.yaml` and were deliberately scaled back rather than faked:

- **No task priority field at all** — `TaskRequest`/`TaskResponse`/`TaskUpdateRequest` have no `priority`. The priority badge/filter from the spec doesn't exist in the UI.
- **No `key` field** (`TSK-104`, `WEB`) on tasks or projects — ids are shown as `#104` instead.
- **No tag entity** — tags are just `string[]` on `Task`/`Project`. There's no tag CRUD, color, or description; `/tags` is a read-only aggregated view computed client-side from task data, not backed by a real tag resource.
- **No global user roles** — only `AdminUserResponse.isAdmin` (boolean) and `.isActive`. Project-level access uses a numeric `roleId` via `ProjectMemberResponse`/`ProjectMemberRequest`. `GET /api/roles` (`RoleResponse` — id/name/description/permissions) **does** exist now and drives the role dropdown in `ProjectMembersModal` (cached in `dictionaries.roles`); it falls back to a raw numeric input if the list is empty.
- **No admin "create user" endpoint** — only self-registration `POST /api/auth/register`. The admin "Пользователь" button on `/people` (`CreateUserModal`) posts to that same endpoint with `{ auth: false }` and discards the returned token, so the admin's session is untouched; the new account is a plain user (no way to set `isAdmin`). `PeopleListView` always probes `GET /api/admin/users`: `200` → admin table (toggle `isActive` / delete / create), `403` → read-only catalog. It does **not** read `auth.isAdmin` at all — starts `isAdminView = false`, the probe upgrades it.
- **Profile & password are editable** — `PUT /api/users/me` (`UpdateProfileRequest`: displayName/email/avatarUrl) and `PUT /api/users/me/password` (`ChangePasswordRequest`). `/profile` has the forms. There is still **no avatar file-upload endpoint** — `avatarUrl` is a plain URL string.
- **AI-agent access** (`ai.md` "вариант 1") — dedicated `/agent` route (`AgentAccessView.vue`, "Доступ для ИИ-агента"; in the user menu + command palette). Everything a person needs to wire an agent up by hand: **token** (`POST /api/auth/agent-token` → `requestAgentToken()`; a 2nd JWT for the same user, groups `USER`+`AGENT`, no `ADMIN`, 48h, no refresh — create/reveal/copy/regenerate/delete), **addresses** (`${origin}/api`, `${origin}/api/agent/openapi.json`) with copy + a "Скачать" button (`fetchAgentOpenApi(bearer)` — direct auth'd `fetch`, not the `http` wrapper, since the URL is `bearerAuth` and can't be opened in a browser), a **ready system prompt**, **example prompts**, a can/can't list, and a **"Всё одним куском"** card — token + addresses + rules + a trailing `## Задача` placeholder as one Markdown blob (`bundle` computed) with "Скопировать всё" / "Скачать .md" (`taskmind-agent.md`), token masked in the preview (`bundlePreview`) but full in the copy/file. Token lives only in `localStorage` (`auth.agentToken`, via the store) — a credential the user pastes into their own AI client, **never** sent by this app (`http.ts` always uses the human `token`). "Удалить" only forgets it locally (server has no revoke). `/profile` keeps just a status line + "Открыть раздел" link. MCP (`ai.md` вариант 2) is **not** built — backend doesn't have it. The `AGENT`-forbidden 403s are server-side; the UI doesn't special-case them.
- **"через агента" attribution** (`ai.md` §3.4) — `CommentResponse.actorType` and `ActivityResponse.actorType`/`.actorSession` (`ActorType` = `HUMAN`|`AGENT`; both `actorType` fields typed optional — server always sends, old rows might not). `components/common/AgentBadge.vue` (subtle `secondary` badge, `i-lucide-sparkles`, "через агента") renders **next to the author name**, never instead of it — in `TaskDetailView`'s comment list and activity card. The activity card also has a `USwitch` "Скрыть действия агента" (only shown when the feed has agent rows) → `visibleActivity` computed. Summary is **not** badged (it has its own `summary_source`); task fields are not badged (`createdBy`/`updatedBy` stay the human). `actorSession` (the token `jti`) is typed but not yet used for grouping.
- **Optimistic locking exists** — `TaskResponse.version` + the optional `X-Expected-Version` header on `PATCH .../tasks/{taskId}` (see `updateTask(..., expectedVersion?)` in `src/api/tasks.ts`). `TaskDetailView` sends the version and shows a "записать поверх / перезагрузить" conflict dialog on `409`; `TaskListView`'s quick table edits deliberately omit the header (last-write-wins).
- **`TaskDetailView` save model** (`task_edit.md` → revised per `task_edit_2.md`, client part) — **no batched Save button**. The sidebar pickers (status, assignee, due/start date, estimate, tags) + archive toggle save **immediately & optimistically** via `saveField(patch)` — a serialized queue (`saveQueue`) so back-to-back edits don't race a false `409`; rollback on error. **Title & description** are the only explicit edits: `InlineEdit`'s "Готово" commits straight to the server (`saveTitle`/`saveDescription` → `saveField`), and its in-progress text autosaves to `sessionStorage` (`draft-key` prop, key `taskmind.taskDraft.desc.<id>`) → on return a "Несохранённый черновик — Восстановить / Отбросить" bar. No `isDirty`, no route-leave guard, no `beforeunload`. The `409` conflict is still object-level (a per-field server conflict is `task_edit_2.md` §3–5, unbuilt); `changeParent`/`convertType` still send no version (`/parent`, `/convert` take no `X-Expected-Version` in the contract).
- **Epics vs tasks** (`parent_task.md`, server done) — `TaskResponse.taskType` (`TASK`|`EPIC`) + `parentId`/`parentTitle` (task→epic) or `childTotal`/`childDone`/`epicClosed` (epic progress, server-computed by children's `isClosed` statuses). An **epic has no assignee, no own status, no time logging** (`assignedUserId`/`statusId` are `null`); its "Списано" is the sum over children. Client's one branch is `isEpic()` (`src/utils/taskType.ts`) — route is shared (`/tasks/:projectId/:taskId`), blocks differ. `TaskDetailView`: `EpicProgress.vue` replaces the status/assignee selectors, `EpicTaskList.vue` is the child list (checkbox flips a child between the project's `isDefault` and `isClosed` status, optimistic, sends the **child's** `X-Expected-Version`; emits `changed` → parent re-`getTask`s for fresh progress). A normal task gets an "Эпик" selector → `PUT /api/tasks/{taskId}/parent` (`setTaskParent`; **not** PATCH — the contract's PATCH can't tell sent-`null` from absent). `⋯` menu has convert → `PUT /api/tasks/{taskId}/convert`. Epic delete: `deleteTask(pid, id, 'detach'|'delete')` (`?children=`), 3-way modal when the epic has children. `TaskFormModal` first field is "Вид" (Задача/Эпик; hidden + forced TASK when a `parentId` prop is set); it now emits `created`. `TaskListView`: flat table has a `?type=task|epic` filter (`FindTasksRequest.taskType`) — epic rows show `i-lucide-package` + a progress badge instead of a status. `GET /api/epics/{id}/tasks`, `GET /api/projects/{id}/epics` (cached in `dictionaries.epicsByProject` / `loadEpics`). `discussion.ts` is still unwired — `parent_task.md` §5.2 explicitly drops the block-discussion tab from the epic page.
- **Epic grouping in `/tasks`** (`tasks_view.md`, client-only) — `?view=epics` (view select in the toolbar). `useEpicGrouping` (`src/composables/`) buckets tasks by `parentId`; epic headers/progress come from `dictionaries.epicsByProject` (a child task carries only `parentId`/`parentTitle`, never the parent's `childTotal`, and `assignedToMe` doesn't return epics). Grouped mode needs one project selected and loads **all** its tasks — `fetchAllProjectTasks` pages `POST /api/find` at `limit:200` (cap 4000); there's **no** server `grouped` flag (`tasks_view.md` §8 unbuilt), so no server change. `EpicGroupHeader.vue` = the collapsible header (`div[role=button]`, Enter/Space, `#id` not a key, `UProgress` only when `childTotal>1`, "· показана N" when a filter hid part of the epic). Collapse state: `useEpicCollapse` stores the *expanded* group ids in `sessionStorage` per project (`taskmind.epicExpanded.<pid>`) — so the default (empty) is **everything collapsed**: you see the epic headers with progress first, expand what you need. "Без эпика" is always last. Auto-switches to grouped when a single project with ≥1 epic is picked (`userChangedMode` / `?view=` in URL blocks that). `Shift`+`←`/`→` collapse/expand all. Empty epics show a "Добавить" link → local `TaskFormModal` with `parentId`. Narrowing filters (search/status/assignee/tags) hide non-matching groups; project choice alone keeps empty epics visible.
- **Status board in `/tasks`** (`status_view.md`, client-only) — `?view=board` in the same view select. Columns = the selected project's statuses (ordered by `statusOrder`, `isHidden` ones not drawn), cards = tasks in the column of their `statusId`; epics never appear (`statusId = null`). Loads all project tasks at once like `?view=epics` (`fetchAllProjectTasks`); `useStatusBoard(statuses, visibleTasks)` builds `BoardColumn[]`. `StatusBoard.vue` (native HTML5 drag on a column wrapper) / `BoardCard.vue`. `moveCard({task, toStatusId})` is optimistic (card moves first), rolls back on error, sends the **card's** `X-Expected-Version`, and on `409` restores the card + refetches (`status_view.md` §6). No server `grouped` flag — no server change.
- **Notifications** (`notifications.md` §1) — `NotificationBell.vue` in `AppHeader`, `stores/notifications.ts` polls `GET /api/notifications/count` every ~45s; the `UPopover` list loads on open. Six `/api/notifications` endpoints (list / count / mark-read / mark-all / settings get+put). Types `MENTION | ASSIGNED | COMMENT | STATUS_CHANGED` (server-side rules: not-your-own-actions, collapse same-type-same-task, per-type mute). Click → task route, resolving `taskId`→`projectId` via `POST /api/find`. Per-type toggles are a card on `/profile`. **No** Web Push / email / SSE / `DUE_SOON` — backend doesn't have them.
- **@-mentions** (`notifications.md` §7 — `MENTION` type) — `MentionTextarea.vue` (used by `InlineEdit` for the task description and by the comment box). `@` opens a list of **project members** (`ProjectMemberResponse`, not `/api/users`); the raw token `@username` goes into the text, rendered as "@Имя" by `MarkdownView` via `src/utils/mentions.ts` (`marked` inline extension). Server turns a mention into a `MENTION` notification for the mentioned user. `EditorHint.vue` (the ⓘ next to the field) is the hover hint for keys + mentions and links into `/help`.
- **Project statuses are editable** — `PUT /api/project-statuses/{statusId}` (`ProjectStatusUpdateRequest`: statusName/statusColor/statusOrder/isClosed/**isHidden**; no `isDefault` or `projectId`). `ProjectStatusResponse` gained `isHidden`. UI: `ProjectStatusesModal`, opened from the `/projects` row menu ("Статусы"). There is still **no DELETE** for a status.
- **Project archiving has no request field** — `ProjectResponse.isActive` exists but `ProjectUpdateRequest` can't set it, so there's no archive/unarchive action, only display of the current state.
- **Task/project list counts and progress are computed client-side** by calling `POST /api/find` with `limit: 1` to read `.total` — there's no aggregate endpoint. Be mindful of request fan-out (one extra call per project) if extending this.
- **`POST /api/find` search fields:** `titleSearch` is a **case-sensitive** substring on the title only (so `"redesign"` misses `"Redesign…"` — near-useless for a search box). `contentSearch` is **case-insensitive** and matches title **and** description. The `/tasks` search box and the command palette both send `contentSearch`; don't switch them back to `titleSearch`. `/api/find` also only returns tasks from projects the caller is a member of. `POST /api/wiki/find` mirrors this — the command palette sends `contentSearch`.
- **Wiki diverges from `wiki.md` in a few places** (API wins): task references in page text are `#123` (numeric id), **not** `TSK-123` — there's no letter key; `WikiBacklinkResponse` is just `{ pageId, projectId, title }` (no `taskId`/`taskKey`), so both `GET /api/wiki/{id}/backlinks` and `GET /api/tasks/{taskId}/wiki` mean "pages that reference X"; `X-Expected-Version` on `PUT /api/wiki/{id}` is optional in the contract but the client **always sends it** (one client, silent overwrites cost more here — `wiki.md` §2.2); there's **no page-move** — `parentId` is set only at creation and shown read-only on edit; there's **no revision-restore endpoint** — restore re-`PUT`s the old snapshot (and sends **no** `summary` — revisions don't store it, `WikiRevisionResponse`/`WikiRevisionDetailResponse` have no `summary`, so a restore leaves the current description untouched). No `jsdiff` dependency — `src/utils/linediff.ts` is a small LCS line differ.
